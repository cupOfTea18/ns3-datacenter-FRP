- 审查日期：2026-09-29。
- 总体判断：**建议局部调整，不需要全面重做。**
- 范围：当前 LonghaulCC R3 的实验场景、配置、统计口径及已有运行证据。
- 工作方式：前序审查只读检查源码、配置与已有 CSV；本文整理该次审查，不代表重新运行验证。此次仅新增本文，没有修改代码或实验配置，没有构建或运行仿真。
- 时效：源码位置与结果描述对应本次会话中的审查快照；后续源码、配置或结果目录变化后，需要重新核验。

## 1. 总体判断

保留现有层次拓扑、S0–S5 的基本分工和双向流量设计。优先调整实验时长、缩小测试的流量关系，并补充一个针对 R3 机制的场景及必要对照。

当前平台已有真实多跳路径、逐流网关控制、消息处理和缩小负载下数据完整性的功能证据，但尚不足以支持预测改善性能、提高公平性、改善短流尾延迟或完整负载无损等结论。

需要区分三类材料：

1. **当前实现与配置**：用于判断程序实际执行什么。
2. **已有运行记录**：仅证明相应源码版本、输入和时长下发生的现象。
3. **设计与实验计划**：说明希望检验的问题，不代表已经实现或验证。

本文使用“已确认”表示审查时由源码、配置或原始记录核实；“推断”表示据事实作出的解释；“建议”表示尚未执行的调整；“待确认”表示当前证据不足。

## 3. 依据与问题

### P0-1：默认 S2 时长不能支持完整 FCT

**已确认：**`config-longhaul.txt:8–10` 选择 S2、0.38 s；`flow-longhaul-s2.txt:3–9` 中七条 3 GB 流在 0.21 s 启动，剩余仅 0.17 s。即使独占 100 Gb/s 主机链路，发送 3 GB payload 也至少需要 0.24 s，尚未计头部、竞争和时延。

**影响：**该默认设置可以用于限定窗口内的瞬态观察，但不能用于完整 FCT 对比。`README.md:102` 仍称默认 S0，与实际配置不符。

**建议：**先确定该运行属于瞬态实验还是有限流完成实验。后者可用 README 中的 1.50 s 作为候选时长，但仍必须核对完成数，不能把候选值写成已验证充分。

### P0-2：缩小测试破坏了 S2、S3、S5 的目标竞争关系

**已确认：**已有验证目录将每条流统一缩小为 1 MB。原始 FCT 与输入显示：

- S2：R3 首流约 38.9 ms 已完成，新七流在 210 ms 才加入。
- S3：八条流全部为 1 MB，与 S1 输入相同，失去“七条先退出、剩余长流继续”的关系。
- S5：背景流约 38.9 ms 已完成，首个探测流在 80 ms 才开始，没有与背景实际重叠。

**影响：**这些测试仍是有效的多流功能检查，但不能证明加入响应、退出后恢复或短流与长流共存性能。停止时间为 0.4 s，不等于存在 0.4 s 的持续拥塞。

**建议：**保留原功能记录；后续缩小性能场景时保留流大小比例与时间关系，不再统一缩成相同大小。

### P0-3：预测触发尚未形成实际控制收益的证据链

**已确认：**`dci-gateway-node.cc:281–285` 仅在预测积压超过 `qref` 时增加排空扣减。重查 S1–S5 的控制日志，超过 500,000 B 的采样时刻，对应 A 组队列均已为空。

S1 的具体例子：

- A 预测积压峰值为 2,996,775.6558 B，发生于 31.95 ms。
- 对应组 A 的最后实际发送在 28.684273 ms。
- B 整次运行的实际组队列峰值仅为 3,144 B。

证据位于 `results/r3-validation-20260929-160143/final/s1/proposed/seedconfig-run1/` 下的 `r3.gateway-40.csv`、`r3.gateway-40.packets.csv` 与 `r3.gateway-81.csv`。

**影响：**非零预测和目标速率下降证明计算路径执行了，不能直接证明限制了后续待发数据或改善了结果。上述预测样本还显示明显高估，需要将预测终点与未来真实队列对齐分析。

**待确认：**持续供给、远端服务变化时，预测是否改变实际发送，以及是否带来增量收益。`PROPOSED_R3_IMPLEMENTATION.md:97` 中“控制信号实际生效”不能扩大解释为已验证预测性能收益。

### P1-1：拓扑适合当前部署范围，但缺少异质下游拥塞对照

**已确认：**`longhaul-r3.h:54–99` 根据真实转发路径识别两端 DCI、B 出口和 PG，并检查反馈回程经过 B。当前拓扑与单对 DCI、固定路径的实现范围相符，不需要改成主机直连 DCI。

S1 多接收端与 S4 双向设计应保留。但多个目的主机并不自动构成“同一 B 出口内，一条流受到下游拥塞、另一条不受影响”的对照。现有流文件也没有明确的多源汇聚同一接收主机的 incast 设计。

**影响：**可以检查多接收端和双向功能，尚不能据此证明逐流反应能保护不受拥塞影响的流。由于没有隔离上游 ECN，B 收到 CNP 也不能自动定位为 B 内部拥塞；该边界已在 `PROPOSED_R3_IMPLEMENTATION.md:66–70` 中说明。

**建议：**优先增加一个现有拓扑上的小型异质拥塞变体；若当前不主张 incast 性能，无需立即增加完整 incast 矩阵。

### P1-2：统计口径会干扰场景判断

**已确认：**[analyze-longhaul.py](../simulator/ns-3.39/examples/LonghaulCC/analyze-longhaul.py) 存在以下问题：

- 第 221–222 行按“单流路径瓶颈÷同向活跃流数”计算公平目标，没有按实际共享链路约束分配容量。
- S1 记录中的 B 出口分组为 2、5、1 条流，实际竞争并不均匀，不能统一套用一个等分目标。
- 第 275–296 行混合两个方向的 DCI 利用率和队列样本，并只使用停止前窗口；其中 `dci_queue_max_bytes` 不是全程峰值。
- 第 413–421 行的 run 级收敛汇总忽略非数值的 `not_converged`，可能掩盖未收敛流。

**影响：**可能将路径约束造成的异质速率误判为不公平，或将完成后的空闲尾段当作低利用率。这些问题不应通过修改场景负载来掩盖。

**建议：**使用实际路径竞争集合确定目标，分方向统计利用率，区分全程峰值与忙时窗口，并同时报告未收敛比例。

### P1-3：完整竞争负载下 baseline 的可信工作状态仍待确认

**已确认：**runner 对算法共用配置和工作负载，具备基本可比性；R3 保留主机 DCQCN，Bifrost 为链路层 Bifrost 加主机 DCQCN。默认每算法只运行一次，README 的五次重复是命令示例，不是执行证据。

TIMELY 的 10.3/11 ms 阈值与约 10.228 ms 基础 RTT 数量级相符，可作为起点，但不能据此认定已公平标定。HPCC、TIMELY、Bifrost 的已有 R3 同期记录主要提供 S0 启动与完成证据，不能替代完整拥塞负载验证。

`BUFFER_SIZE 50` 也不能解释为总缓存仅 50 MiB：`longhaul-convergence.cc:359–363,1124–1145` 另外配置逐端口、逐 PG headroom，并加入 buffer pool。当前 WAN 每 PG headroom 为 375,000,000 B，DC 内 100 Gb/s 端口每 PG 为 56,250 B；headroom 公式未计入配置的 15 μs 接收处理延迟。

**影响：**零丢包、有限缓存以及 baseline 性能结论需要同时说明实际资源和丢弃情况。共享配置是可比性的必要条件，不是 baseline 可信工作的充分条件。

## 5. 最小调整建议

以下均为建议，尚未执行。

| 对象 | 最小调整 | 验证目标 |
|---|---|---|
| 默认 S2 | 区分瞬态与完成实验；完成实验延长停止时间，1.50 s 仅作候选；同步默认场景说明 | 区分停止过早与控制效果 |
| S2 缩小场景 | 使首流在新流加入时仍持续供给，加入后留出明确观察窗口 | 观察新流加入对原流的冲击与再收敛 |
| S3 缩小场景 | 保留七条较小流与一条较大流的差异，并确认退出后剩余流继续供给 | 检验带宽再获取，而非八条等长流同时结束 |
| S5 缩小场景 | 保证有限大小流到达时背景长流仍活跃；若声称稳态叠加，还需证实背景已稳定 | 检验长短流共存，而非孤立短流启动 |
| 一个 R3 机制变体 | 沿用当前拓扑，让同一 B 出口下两类跨域流仅其中一类受到明确下游竞争，并持续供给 | 检验逐流反应、服务估计和有待发数据时的预测排空 |
| 该机制变体的对照 | 优先比较完整 R3 与使用旧快照、不重建的对照；当前需要另行实现消融入口 | 分离预测贡献与普通预算整形贡献 |
| 分析与验收 | 修正路径公平目标、方向与窗口；报告未完成及未收敛比例 | 防止统计口径产生假结论 |

S0 保留用于启动成本和基线核验；S1 保留同步竞争；S4 保留双向反馈检查。现阶段没有证据要求删除整个场景，也不必立即开展大量 RTT、带宽、流规模扫描或全面算法矩阵。

## 6. 结论边界与下一步证据

**当前能够支持：**R3 已有真实层次多跳路径上的实现与功能运行证据；所核验的缩小测试完成了传输、逐流字节闭合和控制消息处理，且这些 R3 运行没有记录到准入丢弃。

**当前尚不能支持：**预测提高吞吐或改善 FCT、加入/退出后更快收敛、异质流隔离或公平性更好、短流尾延迟改善、完整 3 GB 负载无损，以及优于全部 baseline。

最值得补充的是一个稳定、可复核的机制场景，而不是立即扩大运行数量。其证据应连接：

1. 明确位置和时刻的远端服务或拥塞变化。
2. 对应的 B 反应、快照与 A 预算/预测决策。
3. A 仍有待发数据时的实际出队变化，区分目标速率与实际动作。
4. 对齐预测终点的未来 B 队列，以及 goodput/FCT 变化。
5. 相同条件下的消融对照，以及预期 FCT、未完成流、逐流字节、重传和全网 admission drop 检查。

程序退出成功、生成 CSV 或 `status=ok` 只能说明进程与输出状态，不构成上述研究结论的充分证据。
