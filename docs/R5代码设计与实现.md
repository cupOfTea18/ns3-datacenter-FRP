# R5 代码设计与实现

本文件指导将 [R5 方案](R5设计方案一.md) 落实到 ns-3/LonghaulCC。方案文档定义机制和职责；本文件说明源码位置、状态、调用顺序、接口契约、配置及实施依赖。它不是“这些功能已经实现”的声明。

源码核对基于 2026-10-16 的工作区，Git HEAD 为 `88a7366606f508a60e5061b0db8f346cac83b6b7`。下文使用三种标记：

- **现有**：本次从源码确认的行为。
- **计划**：方案已经规定、需要落实的行为。
- **建议**：为落实方案提出的具体编码选择，尚未固定的命名、策略或参数；待决事项集中在第 16 节。

代码框中的新结构和伪代码均为建议，不是现有 API。保留 R5 的算法名称，控制报文与日志应使用独立的格式版本，不能让旧解析器把新结构当作旧组控制。

### 2.2 初始化路径

现有路径：

```text
main()
  → LoadFlows()
  → 按 start_time 调度 StartFlow()
  → Proposed::Setup()
      → DciGatewayNode::Configure()
      → 为控制地址安装路由
      → 遍历 flows；TracePath() 获得逐流路径
      → 给 A、B 分别 RegisterFlow()
      → Start()
  → Simulator::Run()
```

`RegisterFlow()` 使用实验下标加一作为两端相同的流 ID，预填地址、端口、PG、远端出口、正向传播和本地反压响应时间。它没有传入流大小和启动时间，但仍提前知道未来连接和路径。

当前组 ID 按 B 节点、B 出口和 PG 编码；A 每流取得逻辑队列，多条流共享组预测、候选和桶。桶容量来自一帧 `frameBytes`，初值为零，速率设零时清空。源出口逻辑队列从 8 起分配，`BEgressQueue::fCnt=128`，因此当前单出口最多使用 120 个这种额外槽位；超过范围直接终止，没有动态等待、回收和复用流程。

`Start()` 当前拒绝空组表。计划必须允许空流表启动；配置检查也不能再通过未来组数预先分摊整机缓存。

### 2.3 普通数据路径与计数顺序

现有路径：

```text
QbbNetDevice::DoReceive()
  → 解析报文；非 PFC 报文附本地入口 InterfaceTag
  → DciGatewayNode::SwitchReceiveFromDevice()
      → 消费发给本节点的 R5 控制报文
      → 观察原生 CNP/带标记 ACK
      → SwitchNode::SwitchReceiveFromDevice()
          → 既有 atcGateway.packetIn() 分支
          → SwitchNode::SendToDev()
              → GetOutDev()：实际 ECMP 选出口
              → 决定 PG；MMU 检查并扣账
              → QbbNetDevice::SwitchSend()
                  → m_groupClassifier()
                  → BEgressQueue::Enqueue()
                  → QbbAdmitted → DciGatewayNode::Admitted()
                  → DequeueAndTransmit()
```

关键约束：

- `m_groupClassifier` 当前只返回逻辑队列号，不能表示等待或拒绝；未命中时回落到普通 PG 队列。
- 分类发生在 MMU 已扣账之后，`SwitchSend()` 内入队失败当前是断言终止。因此不能把全部动态建表和资源失败处理塞进现有分类回调。
- `LookupOutputPort()` 已存在，使用相同 ECMP 决策；它只能提供当前节点的出口，不能提供 B 尚未报告的出口。
- `InterfaceTag` 是本地 MMU 退账上下文，出队时移除，不能当作跨网关传输的连接信息。
- 既有 atcGateway 分支是基类路径的一部分。Proposed 装配应确认其他网关机制未被误启用，不据此引入新的 ATC 控制行为。

实际出队路径：

```text
QbbNetDevice::DequeueAndTransmit()
  → 更新桶，结合 PFC 和令牌构造 blocked 队列
  → BEgressQueue::DequeueRR()
  → 扣桶令牌
  → SwitchNode::SwitchNotifyDequeue()
      → MMU 退账、必要 ECN 标记和 PFC 恢复检查
  → QbbDequeue → DciGatewayNode::Dequeue()
  → TransmitStart()
```

当前 `QbbDequeue` 在 `TransmitStart()` 之前。现有历史按出队时刻加传播、接收处理和该包序列化时间记录预计 B 到达，前提是传输成功且路径无损。计划中的失败记账不能把此回调无条件等同于成功到达 WAN，见第 5.3 节。

### 2.4 控制与主机路径

现有 B 周期路径是 `Tick() → SampleReceiver() → SendReport()`；暂停变化经 `PauseChanged()` 合并后，在一个控制周期后采样。反馈使用 IPv4 协议号 249（0xf9），通过 `SendNetworkControl()` 走普通路由的优先级 0。

现有 `R5Header` 在网关源文件内定义，内容为组记录的 17 个 64 位字段及版本/字段数量头，总长 144 字节；没有逐流会话与关联查询。A 经 `ReceiveReport() → ApplyRecord()` 接收，按组 ID、来源、时间、顺序和守恒关系校验，再调度 `ActivateSources()`。

A 的周期路径为：

```text
Tick()
  → UpdateSource(group)
  → 按 localWindow 调用 UpdateBackpressure(group)
  → CommitControls()
  → QbbNetDevice::ApplyInjectionControls()
```

当前预测终点是当前时刻加正向传播及一帧序列化，候选为近似的 `net - (predicted.queue - qref) / tau`；没有从当前候选动作生成到 $t+d_b$ 的未来发送轨迹。候选 `candidate` 与调度 `target` 已分离，组内轮询也已有独立游标；这些语义应保留，不能在逐流迁移时回退。

近端 CNP 由 `SendNearCnp()` 使用模拟源 UDP 端口与 PG 构造。主机 `RdmaHw::ReceiveCnp()` 以接收方 IP、源 UDP 端口、PG 查找发送 QP，再进入 `cnp_received_mlx()` 等 DCQCN 状态更新。B 观察原生 CNP 只记账并透传，没有独立下游限速。

PFC 在 `DoReceive()` 内按 PG 处理：正暂停刷新到期事件，零时长或到期调用 `Resume()`。普通交换机 PFC 通过 `RefreshPfc()` 续发，出队时检查解除。分析暂停需使用合并的状态区间。

### 2.5 现有地址分配及其依赖

当前 `NodeAddress()` 根据节点 ID 与两个 DCI 节点 ID 的大小关系推断 DC，生成 `11.<dc>.0.<node_id+1>`，并限制节点 ID 小于 254。`AssignNodeAddresses()` 在建链路前填写 `serverAddress`、`ipToNodeIdMap`，对交换机调用 `SetSwitchRealIp()`。

建链路时，主机先通过 `AddAddress()` 获得上述 `11.* /8` 地址；随后 `Ipv4AddressHelper::Assign()` 又为链路两端分配 `10.* /24` 地址。因此当前主机接口有两个非回环 IP。`StartFlow()` 和 `SetRoutingEntries()` 使用 `serverAddress`，RDMA 数据使用 `11.*`；PFC 构包则读取设备对应 IPv4 接口的第一个地址。

地址不能只从 `AddAddress()` 一处删除。`ip_to_node_id()`、`FindFlow()`、`FindRxQp()`、完成回调、路径记录和元数据均依赖端点地址；`SwitchNode::TrackActiveFlow()` 与 `RdmaHw::HandleFrpFeedback()` 还读取数据端点 IP 的第二个字节判断 DC。R5 的 `ControlAddress()` 另用 `172.31.*`，属于网关控制通道，不是主机的第二个 IP。第 4.4 节规定统一后的地址计划和更新顺序。

## 4. 标识、状态与计量契约

### 4.1 FlowKey、FlowID 和代际

**计划**：真实网络与仿真使用相同语义的 FlowKey，只包含 `Src IP`、`Dst IP` 和 `BTH.DestQP`。网络命名空间、PG、UDP 源/目的端口、实验流编号都不加入该键。前提是两个 DC 的主机 IP 全局唯一，并且 A、B 观察到相同的端点地址；基础实现不支持重叠地址或 NAT。

建议采用以下数据组织；名称可以调整，匹配字段不能替换：

```cpp
struct FlowKey {
    uint32_t srcIp;
    uint32_t dstIp;
    uint32_t destQpn;  // 解析自 BTH.DestQP；按所用报文格式检查有效范围
};
```

查表比较三个字段的完整值，哈希相同不能直接视为同一流。相同 IP 对的不同目的 QPN 独立建表；相同三元组的 UDP 端口或 PG 变化不创建第二条流。PG 仍作为队列/PFC 属性保存，变化时按第 12.4 节处理关联失效或不支持的迁移，不能追加到 FlowKey 来绕过处理。

**现有差距与计划的报文路径：** 当前 `DciGatewayNode::Match()` 查找 `(sip, dip, sport, dport, pg)`，`CustomHeader` 解析 UDP、PG 和序号，没有 BTH.DestQP；`RdmaHw::GetNxtPacket()` 生成的也是现有 `SeqTsHeader + UDP` 模拟格式。因此必须同步落实以下依赖：

1. 端点连接状态保存本地 QPN 和对端 QPN。**建议**由各主机的端点模块分配本地 QPN，在连接建立时向对端提供；目的 QPN 是接收端 QP 的身份，不由网关生成，也不直接采用实验行号或 UDP 端口。端点之间建立连接不等于向网关预注册流。
2. 发送端把对端 QPN 编入数据报文的目的 QPN 字段；接收端据此关联自己的 QP。发包头、`CustomHeader` 的序列化/解析、头长、MTU、`frameBytes` 和统计扣头必须一致。具体 BTH 编码或明确建模其字段的模拟头布局，以及端点交换方式，列为 D6；不能只增加一个未序列化的成员或 `PacketTag`。
3. A、B 均从实际到达的数据解析三个字段，并在各自首次未命中时建表。受控数据缺少目的 QPN、头部截断或取值非法时明确拒绝并计数，不回退到端口键。反馈中的 FlowKey 也使用同一三元组和明确的字节序。
4. 一个主机内同时存在的 QP 不能分配到同一本地 QPN；不同主机可使用相同 QPN，由端点 IP 区分。端点的分配耗尽、销毁和重用须有规则；控制代际不能解决真实 QPN 过早重用造成的旧包混入。

其余标识与 FlowKey 分开：

```text
FlowKey          // (Src IP, Dst IP, BTH.DestQP)
FlowID           // 本地记录编号；不要求 A、B 相同
FlowHandle       // 本地槽位 + 本地创建代际
g_A, g_B         // 对端会话身份 + 本地单调创建序号
ResourceKey      // 网关/端口/真实队列或缓存池/目的资源身份
```

A、B 本地 FlowID 不必相同。保护期内恢复保留代际；彻底删除后再建用新代际。控制代际不能冒充真实 QP 连接代际。任何跨网关标识都必须可通过控制报文或真实数据传递，不能偷偷传 ns-3 全局对象、Packet UID 或仅本地可见的 Tag。

发送端 CNP 查找所需的关联信息单独保存，不扩充 FlowKey。当前主机的端口/PG 查找方式是模拟端点接口的现状，不是新 R5 的流身份；具体过渡与源 QP 信息要求见第 11 节和 D6。

### 4.2 状态分配

以下为建议的数据组织，字段名称可以调整，含义不能合并。

| 对象 | 必要字段 |
|---|---|
| 通用流记录 | FlowKey、FlowHandle、角色、对端、PG、本地出口、生命周期、最后数据活动、空闲起点、保护截止、待处理字节、操作引用数 |
| A 控制状态 | 实际累计 $X_f$、有界发送历史、$r_f^{\mathrm{cap}}$、实际 $r_f$、有效反馈/绑定、B 资源关联、供给统计、未核销计数、冻结预测、恢复与保护原因 |
| A 执行状态 | $K_f,z_f$、上次令牌结算时刻、执行速率、逻辑队列、当前许可、流/队列代际 |
| B 测量状态 | 成功入队、出队、入队前/后丢弃、实际驻留、实际资源关联、采样序号、$g_B$ |
| 排队资源 $e$ | 所属端口/PG、$Q_e$、背景累计、出队累计、区间排空标志、暂停累计与当前暂停、有效容量与服务估计 |
| 带宽资源 $a,p,d$ | 成员流、预算、来源、有效期、与其他入口的份额关系 |
| 缓存资源 | 物理池身份、总容量、普通队列占用、等待缓存占用、必要保留量、风险余量 |
| A 反压状态 | 本地缓存范围、窗口输入/输出、$Q_H,Q_L,\tau_{\mathrm{local}},M_A$、保护状态、QP 通知时刻与原生通知时刻 |
| 回收保护记录 | FlowKey、代际、余额、必要基线和绑定、截止时间；计入同一身份池 |

执行器是令牌余额的唯一写入者。预测器读取决策时刻的余额快照，在副本上推演；不能维护另一个随时间独立累加的“预测真余额”。释放空队列前结算令牌并将必要余额存入保护记录，恢复绑定时转回执行器，保证只有一个有效所有者。

所有累计字节使用足够宽的整数并检查溢出；速率计算可用浮点，但须拒绝 NaN、负值和无穷值。内部时间建议使用 ns-3 `Time`/整数纳秒，公式中的时间差转换为秒。

### 4.3 计数与资源边界

统一使用完整序列化报文字节。常规队列驻留满足：

$$
q_f=I_f-D_f-L_f^{\mathrm{after}},
$$

其中 $I_f$ 为成功进入该计量范围的字节，$D_f$ 为正常出队离开该范围的字节，$L_f^{\mathrm{after}}$ 为仍在该范围内被丢弃的字节；两类离开事件互斥，入队前丢弃不加到 $I_f$。已出队后发生的发送失败另记，不能再次从队列驻留量扣减；A 的成功 WAN 注入 $X_f$ 也不能包含失败发送。每次重传都消耗链路和队列，应按实际副本计数；接收唯一 goodput 单独统计。

等待缓存必须有独立占用账。**建议**将尚未进入常规队列的等待报文作为独立驻留范围，提升为常规队列时做一次原子转移，不能两边都加字节或两边都不计；同一流的等待字节另存，不让普通队列空误触发老化。预测的 $Q_e$ 与反馈必须使用同一范围，共享缓存风险另外加入全部等待占用。具体 MMU 接入见第 5.2 节及 D7。

当前 `CONTROLLED` 用于区分采样同一纳秒内已包含的受控到达。动态代际后，只有建立了可验证的累计起点，才能比较 A 与 B 的累计值；接收首份状态本身不自动建立这种字节基线。无法对齐时设置 `counter_alignment=unknown`，不得跨段相减，见 D8。

### 4.4 两个 DC 的唯一主机 IP

**计划目标**：每台主机只有一个用于网络通信的非回环 IPv4 地址，该地址同时作为网卡接口地址、RDMA 源/目的地址和统计映射地址。`127.0.0.1` 不计入这一要求。基础拓扑要求每台主机只有一条接入链路；多网卡或多宿主场景需要另行定义地址与连接绑定，不能再次自动添加别名掩盖歧义。

#### 4.4.1 按 Leaf 划分主机子网

**计划**：每个接入 Leaf 对应一个独立的 `/24` 主机子网，同一 Leaf 下的主机共用该前缀。由公共拓扑装配使用以下地址规划，Proposed 与 DCQCN 等对照使用相同规则：

| 用途 | 地址池 | 分配方式 |
|---|---|---|
| DC1 的主机子网 | `10.1.0.0/16` | 每个 Leaf 一个 `10.1.<leaf_index>.0/24` |
| DC2 的主机子网 | `10.2.0.0/16` | 每个 Leaf 一个 `10.2.<leaf_index>.0/24` |
| 交换机之间的链路，包括 WAN | `10.3.0.0/16` | 每条链路一个 `/30`；按稳定端点顺序分配偏移 1、2 |

`/16` 仅作为 DC 地址池；主机接口掩码是 `/24`（`255.255.255.0`），交换机间链路接口掩码才是 `/30`（`255.255.255.252`）。网关控制地址继续使用独立的 `ControlAddress()` 与控制路由，并检查其与上述地址池不重叠；不向主机再配置控制地址。

地址规划只读取网络拓扑，不读取实验流列表。先读入全部链路，移除配置中 A—B 的 WAN 边，再以 `DCI_LEFT`、`DCI_RIGHT` 所在连通分量分别确定 DC1、DC2；不再根据节点 ID 大小猜测归属。基础实现要求得到两个互斥分量且覆盖所有节点，主机度为 1、对端为接入交换机；不满足时在启动前报拓扑错误。其他 WAN 结构需要显式的 DC 归属配置后再支持。

在每个 DC 内按 Leaf 节点 ID 升序分配从 1 开始的 `leaf_index`，在每个 Leaf 下按实际接入主机的节点 ID 升序分配从零开始的编号 $h$。主机分组由真实邻接关系确定，不能按全局主机 ID 每八个切分；默认拓扑每组八台只是当前配置。建议分配规则为：

```text
subnet          = IPv4("10.<dc>.<leaf_index>.0")
host_ip         = subnet + h + 1
leaf_access_ip  = subnet + 254 - h
access_mask     = /24
```

当前 Qbb 拓扑为每台主机建立独立的点到点链路，Leaf 的每个接入端口也是独立设备；`SendPfc()` 会读取该设备的接口 IP。因此，**建议在当前模拟模型中**，主机从 `.1` 向上取地址，Leaf 对应接入接口从 `.254` 向下取不同地址。八台主机使用 `.1–.8`，八个 Leaf 接入接口分别使用 `.254–.247`。这些接口地址不是八个子网，也不是主机的附加地址；不能把同一个 `.254` 重复配置到所有接入端口并当作已实现共享网关。

该端口地址分配是现有点到点模型的适配，不要求真实 Leaf 的每个二层端口都有 IP，也不宣称已经模拟共享二层网络或 SVI。基础 RDMA 数据继续使用第 4.4.3 节的精确主机路由；ARP、广播域与普通 IP 网关行为需要另行建模。

建议 `leaf_index` 使用 1–254，0 和 255 保留；`.0` 与 `.255` 不分配给端点。为保证主机和 Leaf 端口地址不相交，该适配要求每个 Leaf 的主机数 $H$ 满足 $2H\le254$，即最多 127 台。这是所选模拟接口分配方式的限制，不是 `/24` 对主机数量的一般结论。超过容量时拒绝配置，不能回绕或复用地址；其他模块的节点数、端口数和状态上限仍独立检查。

交换机间链路按规范化端点对排序编号，在 `10.3.0.0/16` 中按步长 4 分配 `/30`，两端使用偏移 1、2；该池最多容纳 16384 条链路。现有 `nbr2if` 不能区分同一节点对的平行链路，基础设计直接拒绝该情况。

当前默认拓扑的完整计划如下，表中地址尚不是当前程序的运行值：

| 主机组 | 接入 Leaf | 主机子网 | 主机地址范围 |
|---|---|---|---|
| 0–7 | 32 | `10.1.1.0/24` | `10.1.1.1–10.1.1.8` |
| 8–15 | 33 | `10.1.2.0/24` | `10.1.2.1–10.1.2.8` |
| 16–23 | 34 | `10.1.3.0/24` | `10.1.3.1–10.1.3.8` |
| 24–31 | 35 | `10.1.4.0/24` | `10.1.4.1–10.1.4.8` |
| 41–48 | 73 | `10.2.1.0/24` | `10.2.1.1–10.2.1.8` |
| 49–56 | 74 | `10.2.2.0/24` | `10.2.2.1–10.2.2.8` |
| 57–64 | 75 | `10.2.3.0/24` | `10.2.3.1–10.2.3.8` |
| 65–72 | 76 | `10.2.4.0/24` | `10.2.4.1–10.2.4.8` |

例如主机 0 使用 `10.1.1.1/24`，主机 7 使用 `10.1.1.8/24`，主机 8 使用 `10.1.2.1/24`。节点重新编号或更换拓扑后重新输出 Leaf—子网—主机映射，不能继续套用这张默认拓扑表。

#### 4.4.2 唯一地址来源与初始化顺序

保留 `serverAddress[node_id]` 作为现有调用方的地址查询表，但它只缓存实际接口地址，不负责另外生成或配置一个“逻辑主机 IP”。移除建链路前调用旧 `AssignNodeAddresses()` 的流程，将 `NodeAddress()`/`AssignNodeAddresses()` 的职责改为地址规划、实际接口绑定和映射登记，避免保留第二套地址来源。建议按以下顺序调整 `longhaul-convergence.cc`：

1. 读取并校验完整拓扑，计算 DC 归属、Leaf 子网及实际接入主机列表；地址分配不依赖流数、QP 数、PG 或应用启动时间。
2. 创建节点、协议栈和设备。地址编号按上述稳定顺序规划，设备仍可按原拓扑行顺序安装，避免为了排序地址而改变端口编号。
3. 每个接口只配置一次地址。接入链路分别为主机设备、Leaf 设备配置上述计划地址和 `/24` 掩码；使用 `Ipv4AddressHelper` 时，分别指定计划起始地址，再对单设备容器执行 `Assign()`，不能每条接入链路都重置为 `.1` 并给两端顺序分配。交换机间链路仍对按规划端点顺序排列的双设备容器分配 `/30`。删除原先额外添加 `11.* /8` 和原通用逐链路 `10.* /24` 的路径，避免重复分配。
4. 通过 `GetInterfaceForDevice()` 取得真实 IPv4 接口，确认主机唯一非回环接口上只有一个地址；将它写入 `serverAddress`。接口地址、`serverAddress` 和 QP 的 `sip/dip` 必须一致，不硬编码接口编号 1，也不取“第二个地址”。
5. 构建 `ipToNodeIdMap`；地址插入必须检查已有归属，不能覆盖冲突。主机仅登记唯一接口 IP。其他节点可登记各自实际接口地址，交换机 `SetSwitchRealIp()` 建议选用其数值最小的已配置非回环接口地址，不再生成额外的 `11.*` 身份。该选择不是 DC 归属信息；DC 归属由拓扑表和端点前缀给出。
6. 安装 RNIC，执行 `CalculateRoutes()`、`SetRoutingEntries()`，再装配网关控制路由和空流表。该 RDMA 地址模式不调用现有的 `Ipv4GlobalRoutingHelper::PopulateRoutingTables()` 来解释多个接入端口上的同一 `/24`，具体转发约定见下节。应用启动和统计均读取同一 `serverAddress`；网关只获得网络配置，仍在首包到达时发现流。

交换机可以有多个端口 IP；“每个主机一个 IP”不要求交换机只有一个接口地址。已有 `172.31.*` 控制端点也不加入主机地址表或 FlowKey。

#### 4.4.3 路由、PFC 和统计同步

**现有路径依据**：`QbbNetDevice::DoReceive()` 将非 PFC 报文交给交换机自定义转发；主机侧的 RDMA 报文交给 `RdmaHw`，TCP 才另走普通协议栈。`SetRoutingEntries()` 已按目的主机 IP 安装精确表项。**计划**保留该 RDMA 转发路径：同 Leaf 主机经过 Leaf 的目标接入端口，跨 Leaf/跨 DC 经过拓扑计算的下一跳，不以相同 `/24` 推断两个 Qbb 链路直接相连。

| 路径 | 实现要求 |
|---|---|
| RDMA 数据与 ACK/CNP | `StartFlow()` 与端点收发统一使用真实主机接口 IP；ACK/CNP 的返回目的仍是对应主机的唯一 IP，QP 关联独立核对 |
| 自定义路由 | `SetRoutingEntries()` 以同一个主机 IP 安装目的地址到出接口的精确表项；保留拓扑寻路和 ECMP，地址池前缀不替代逐跳路由 |
| 普通 IPv4 路由 | 基础 RDMA 工作负载使用上述自定义表和网关控制路由，不依赖普通全局路由；若新增 TCP 或 socket 控制流量，须另行提供适用于该接入模型的路由与链路层行为，不能仅调用 `PopulateRoutingTables()` 就宣称共享子网已经可用 |
| PFC 源地址 | 保证 `SendPfc()`、`SendPfcWithTime()` 读取的是发送设备对应 IPv4 接口的唯一地址；核对 `m_ifIndex` 与 IPv4 接口索引一致性，必要时用设备查询接口；PFC 仍按 PG 执行 |
| DC 判断 | 主机前缀 `10.1/16`、`10.2/16` 保留第二个字节为 1、2 的含义；对现有 FRP 路径增加有效前缀检查，不把链路地址或控制地址解释成主机 DC。R5 的 A/B 角色继续由实际 WAN 方向确定，不由 FlowKey 增加 DC 字段 |
| 统计与路径记录 | 更新 `ip_to_node_id()`、QP/流统计关联和路径构造，记录节点、DC、Leaf、子网、设备/接口、IP/掩码及地址计划版本；实验编号仅在统计侧关联到实际 QP |

改变 IP 可能改变 ECMP 哈希结果，即使拓扑和端口编号未变也不能承诺路径完全相同。后续对比运行必须共用地址计划，记录实际路径；不能把地址变化带来的路径差异当作 R5 控制收益。

## 5. 初始化、首包准入与实际数据事件

### 5.1 空表启动

计划中的装配顺序：

```text
读取完整拓扑，确定两个 DC、Leaf 子网和实际接入主机
构建节点/设备/MMU；每个接口只分配一次计划地址
从唯一主机接口 IP 填写 serverAddress 和 IP 映射
安装 RNIC 和目的主机 IP 的精确数据路由
配置网关的 WAN 端口、对端控制地址、容量与时延来源
配置有限资源池和 MTU/帧字节口径
安装数据准入、成功入队、真实出队、暂停与控制回调
启动网关周期任务，逐流表为空
实验模块按工作负载启动应用；数据真实到达后建表
```

`Proposed::Setup()` 不遍历未来流来调用 `RegisterFlow()`，不计算逐流 B 出口、本地完整响应路径或创建组。网络基础配置可以使用拓扑信息安装路由，但不能把逐流路径追踪结果注入控制状态。统计侧如保留路径记录，必须与控制器读取路径隔离。

### 5.2 准入扩展及失败顺序

**建议新增的接口契约，不是现有方法：**

| 建议接口/事件 | 调用位置 | 契约 |
|---|---|---|
| `PrepareDataAdmission(packet, ingress, egress, pg)` | 基类已经确定出口和 PG、尚未扣 MMU 之前 | 返回 ADMIT/HOLD/DROP 及有效流/队列句柄；非 R5 数据保持原路径 |
| `CommitDataAdmission(handle, bytes)` | 常规 MMU 和逻辑队列均成功后 | 只计一次成功入队，提交预留资源 |
| `AbortDataAdmission(reservation, reason)` | 提交前任意失败 | 释放临时预留；不重复满桶、不泄漏 MMU 记账 |
| `ResumePending(packet)` | 资源释放或等待重试事件 | 重新检查路径和许可；原子转移等待占用，保持流内顺序 |
| `ReleaseFlowQueue(handle)` | 空队列退出调度且旧引用解除后 | 释放绑定，保留流代际与余额；非空拒绝 |

在 `SwitchNode::SendToDev()` 的准确出口处增加小范围扩展，比在 MMU 扣账后的分类回调中处理失败更直接。默认实现继续原路径；原 `m_groupClassifier` 可保留为已完成准入后的纯分类，不能再为受控的未知流默认返回普通 PG。

首包伪代码：

```text
on_data(packet, chosen_egress, pg):
    key = extract_visible_key(packet)
    flow = lookup(key)
    if flow exists:
        cancel_pending_retirement_on_data(flow)
        validate_role_route_and_attributes(flow, chosen_egress, pg)
    else:
        reservation = reserve_bounded_identity_and_required_state()
        if failed: return bounded_hold_or_drop(packet, STATE_FULL)
        flow = prepare_unpublished_record(reservation)

    if local role is A:
        acquire_or_restore_logical_queue(flow)
        if failed:
            abort_uncommitted_reservations_only()
            return bounded_hold_or_drop(packet, QUEUE_FULL)
    reserve_normal_buffer_or_pending_transfer()
    if failed: rollback_uncommitted_resources(); return hold_or_drop
    if new record: initialize_full_bucket_once_before_enqueue()
    expose_valid_handle_to_admission_callbacks_without_waking()
    enqueue_with_valid_handle()  // 成功回调内提交缓存转移和入队计数
    if failed: rollback_uncommitted_resources_and_buffer_charge(); return drop
    schedule_coalesced_activation_after_callbacks()
```

真正新建记录与报文准入的事务边界须一致：临时预留不对控制器可见，失败回滚不得产生重复可消费额度；已提交的保留记录则沿用原余额。成功计数由入队回调承接，主路径不能再次累加；若设备入队接口会立即唤醒发送，所有准入提交必须先在该回调内完成。B 同样先取得测量资源再准入首包，但仍使用真实物理 PG 队列正常转发。

等待缓存不能成为 MMU 之外的无限旁路。**建议**从同一物理缓存预算中划出有限等待区，普通准入和等待转移共同检查总占用，并让 PFC 压力计量包含它。具体采用 MMU 预留接口还是统一准入计数需要在 D7 确定；不能只加一个 `std::deque` 而忽略缓存/PFC。

### 5.3 出队、历史与失败

计划的顺序是：先验证可发送及历史记录空间，再选包，原子扣令牌与共享许可，退出队列并退 MMU，最后记录真实 WAN 注入结果。

现有 `QbbDequeue` 仍可计队列离开；**建议**补充明确的发送提交/失败事件，或调整 R5 历史记录点，使 `TransmitStart()` 失败不生成虚假的远端到达。失败包已经出队时记录独立发送失败计数，不能再扣一次队列驻留，也不能算成成功链路发送。进入链路后发生的丢失另行记录；远端丢失只有通过实际可达的反馈才能成为 A 的控制输入，全局仿真丢包轨迹只用于事后诊断。重传是新的实际发送事件，不修改旧事实。

首次发送就必须记录历史，不能等 B 关联成功才开始。B 资源尚未知时按本地流与对端暂存，取得关联后再使用，不倒推或改写过去控制决策。

A 的本地“成功入队后立即可发送”可能发生在同一事件。状态、计数和桶必须在唤醒前完整可见。控制激活可使用与现有 `ScheduleNow` 相同的合并原则，但提交全部速率和许可后才唤醒设备。

## 6. 消息、关联与反馈处理

### 6.1 消息语义

保留现有受路由控制报文通道是建议；消息内容不能继续复用只含组记录的旧格式。下列类型为建议命名。

| 类型 | 触发与必要内容 |
|---|---|
| FLOW_STATE | B 首包入队后及周期主动发送：FlowKey、B 会话/代际、序号、采样时间、资源关联、驻留与累计计数；A 不发查询 |
| RESOURCE_STATE | 端口/队列/缓存/目的资源身份、服务与暂停、背景占用、容量预算、来源、有效期，以及状态资源不足/恢复 |

每个报文有格式版本、类型、长度、发送方控制会话。批量记录要有数量上限和完整长度校验；共享状态不必逐流重复。控制发送占用真实链路，统计字节和等待时间。源/目的控制地址须与已配置对端一致。

MTU、批量大小、合并延迟和控制速率上限尚待配置。禁止无限高优先级控制洪泛；也不能让数据暂停完全阻断必要恢复反馈。重启会话识别方式见 D5。

### 6.2 关联与更新顺序

1. A 首包建表并获得四帧满桶，首包入队后安排同一仿真时刻的带宽分配，所有新流仍共享出口及已知目的容量约束。
2. B 首包入队及物理计数更新完成后，立即安排资源与流状态采样发送；后续按周期主动发送，不依赖 A 查询。
3. A 仅查已有数据记录，校验对端会话、FlowKey、B 代际、采样时间、序号、资源与计数，然后直接保存首份状态。
4. 后续状态维持同一 B 代际并单调更新；状态不能重置 A 令牌或发送历史。当前保留身份且会话内不重用 QPN，不支持无证据的跨代重新绑定。
5. 有效状态进入下一控制周期的预测调速；重复或丢失首份反馈不影响数据启动，周期反馈提供后续更新机会。

建议接收伪代码：

```text
receive_control(message):
    validate_version_length_peer_session_and_bounds()
    if resource_only:
        validate_resource_sequence_and_age(); update_resource(); return
    flow = find_existing_record(message.key)
    if absent: count_rejection(NO_LOCAL_STATE); return
    validate_B_generation_and_local_creation_time()
    validate_sequence_sample_time_age_and_counter_consistency()
    commit_snapshot_atomically()
    schedule_control_recompute()
```

普通反馈不能创建流、增加额度或刷新空闲计时。样本年龄大于 $F_{\max}$、采样早于 A 本地建表时间、重复或倒序时拒绝当前控制更新。时间比较服从两端时间戳可对应的前提。

新鲜状态也可能缺乏完整历史：保留其当前观测及明确的资源限制，标记不能正常重放；不能把缺失到达当成零。恢复需要新的可覆盖采样，不因没有进一步拥塞通知自动解除。

## 7. B 观测、服务估计与恢复事件

### 7.1 必须由数据事件维护的量

成功入队、出队、丢弃分别更新逐流和真实物理队列计数。非 R5 数据进入同一资源时记入背景范围，不能从总队列中漏掉。

每个统计区间维护 `emptied_in_interval`；队列任何一次变为零就置位，到下一采样重新开始统计。暂停累计使用设备的实际状态区间；重复 PFC 刷新不等于再次进入暂停。容量、路由或调度变化使旧服务估计失效。

B 的统计和采样不读取 A 的目标速率作为实际到达，也不把 B 自己的高队列转换成主动降速。

### 7.2 总服务与暂停可用性

当前实现已经区分未暂停服务与区间可用比例：

$$
a_e=\frac{\Delta t-\Delta t_{\mathrm{pause}}}{\Delta t},\qquad
\overline y_e^{\mathrm{unpaused}}
=\frac{\Delta D_e}{\Delta t-\Delta t_{\mathrm{pause}}}.
$$

只有持续积压、未暂停时间为正、状态可比时，后一项才是可用估计。当前代码在非暂停采样点反馈近似的未暂停服务乘 $a_e$，当前明确暂停则服务取零。

计划中保留未暂停能力、过去可用比例、当前暂停三个独立量，按方案服务规则使用。独占出口恢复且条件已知时可恢复有效容量；共享出口用仍适用的估计和新观测校正。不能在已恢复的未来区间无限沿用过去的暂停折扣，也不能把过去有吞吐误当作当前未暂停。

B 已有暂停变化后一个控制周期合并采样的机制可作为基础。周期与状态变化同一时刻发生时只形成一致的一份样本；零长度区间不计算速率。

### 7.3 单流服务与目标队列

计划要求 $\sum_f\Delta\widehat D_f$ 与共享资源服务一致，但 B 当前没有逐流公平 FIFO。具体 $\widehat\mu_f$ 策略是 D2，不能默认把端口服务等分后称为实测服务。

**建议接口** `EstimateService(resource, flow_observations, horizon)` 输出：

- 共享资源可用服务、状态和可信程度；
- 逐流服务估计及其调度假设；
- 暂停流的零服务约束；
- 未知或过期状态，不以数值零冒充“确定无容量”。

目标 $q_f^\star$ 从共享 $Q_e^\star$ 分配，受真实缓存和背景占用约束。服务分摊与目标分配的具体策略必须在实现前确定并记录；不把上一轮 A 的实际份额作为永久服务能力。

<a id="impl-s8"></a>
## 8. 实际历史、未来计划与队列预测

### 8.1 时间与字节

内部统一字节/秒和纳秒时间戳，公式时间差用秒：

$$
T=d_f+d_b,\quad F=t+T,\quad h=t+\delta_a+d_f,\quad L=T-\delta_a-d_f.
$$

未来计划只延伸至 $t+d_b$；若 $L\le0$，不执行该终点的候选反解。$T$ 不是主机端到端 ACK RTT。

当前注册传播量不含每包序列化，现有历史另外加序列化与接收处理。新模型必须明确从哪个发送事件到哪个 B 入队事件计时；对每包采用 $\text{arrival}_i=\text{tx}_i+d_{f,i}$ 时，不能又叠加已经含在 $d_{f,i}$ 内的序列化。参考 $d_f$ 与包级 $d_{f,i}$ 的来源和差异要进日志，见 D1。

### 8.2 历史和供给

建议历史条目包含本地代际、发送顺序、发送时刻、字节、预计 B 到达时刻、计数基线与路径版本。不能只保存配置速率。历史池有硬上限；发送前需要记录空间。

未来供给 $\widehat H_f(t,v)$ 只能来自 A 当前队列和近期入口观测。窗口长度、恢复时采用何种趋势以及异常截断属于 D3；严禁读取未来应用发送时间表。

对所有未来时刻满足：

$$
\widehat{TX}_f(t,v)\le q_f^A(t)+\widehat H_f(t,v),\qquad
\widehat{TX}_f(t,v)\le z_f(t)+\int_t^v r_f(w)\,dw.
$$

分段推演必须保留供给到达顺序、桶溢出、PFC、共享许可和物理串行化。未来段的 $r_f=0$ 表示停发，不因 $z_f>0$ 放行。

### 8.3 重放算法

采用方案的 $\widetilde X_f$：

$$
\widetilde X_f(v\mid t,\mathbf r)=
\begin{cases}
X_f(v),&v\le t,\\
X_f(t)+\displaystyle\int_t^v\widehat x_f(w\mid t,\mathbf r)\,dw,&v>t.
\end{cases}
$$

建议流程：

```text
Predict(snapshot, actual_history, candidate_rates, supply_model):
    validate_identity_age_history_coverage_and_time_basis()
    clone_actual_queues_tokens_permissions_and_scheduler_state()
    future_tx = simulate_A_departures_until(t + d_b)
    arrivals = map_actual_and_candidate_departures_to_B()
    split_at_arrival_service_pause_empty_and_sample_boundaries()
    replay_from_sample_s_to_F:
        serve_only_bytes_that_have_arrived
        respect_B_actual_scheduling_and_pause_constraints
        update_per_flow_residence_and_shared_resource_totals
        track_peaks_only_in_[t,F]
    return endpoints, trajectories, pool_peaks, assumptions, validity
```

总量递推为：

$$
\widehat Q_e(u_{k+1})=
\left[\widehat Q_e(u_k)+\sum_{f\in e}\Delta\widehat A_{f,k}
+\widehat b_e(u_k)\Delta_k-\widehat c_e(u_k)\Delta_k\right]^+.
$$

单流出队不能超过已到达可服务字节，逐流与背景服务之和不能超过总服务。总量模型已加背景到达时不再减第二遍背景；若使用净服务 $c_e-b_e$，则对应的到达项中不重复加背景。

同一时间戳内，采样包含哪些包必须由可对齐计数或明确事件边界判断。当前组累计计数技巧不能未经验证直接迁移到独立代际。无法判断的边界标为不确定，使用保守边界或放弃该次精确校验，见 D8。

### 8.4 风险与冻结记录

按完整 $[t,F]$ 检查：

$$
\widehat Q_{e,\mathrm{peak}}=\max_{u\in[t,F]}\widehat Q_e(u),\qquad
\widehat Q_{e,\mathrm{peak}}+M_e\le B_e.
$$

共享池使用同一时刻各真实驻留位置之和，不把各队列分别取得的整机容量叠加，也不混入重复的目的资源视图。建议另外推演受许可和物理上限约束的较高供给轨迹用于风险检查，具体模式见 D3。

每次执行动作都冻结反馈、资源状态、时间、供给/服务假设、余额、许可、最终分配、轨迹及风险结果。滚动重算不覆盖旧记录。后续同时计算原始预测残差与实际输入重放残差，记录计划变化；服务或时延诊断不能仅凭前者归因。

校验时间要与 B 实测一致；终点不落在采样时刻时保存可对齐的预测轨迹点。到校验截止仍缺少观测的记录标记缺失并释放，不能用实际未来数据填回旧快照。

## 9. 候选上限、重叠预算与最终复核

### 9.1 候选与有效性

对可正常预测的流：

$$
r_f^{(0)}
=\left[\widehat\mu_f+\frac{q_f^\star-q_{f,h}}{L}\right]^+,\qquad
q_{f,h}=\widehat q_f^B(h\mid t).
$$

用物理、反馈和风险条件形成 $r_f^{\mathrm{cap}}$。服务明确停止时发送资格关闭；没有 B 状态时以本地物理容量作为候选上限，在共享出口和已知目的容量内尽快发送；状态过期或历史缺失时不能把上述式子的未知项填零后照常使用。

候选上限与实际分配分别存储。若空闲或 PFC 使本轮 $r_f=0$，不得用该零份额钳制下一轮候选。上一候选已因真实风险归零时，恢复依赖新有效状态和重新预测，而不是仅凭时间或队列重现解除保护。

### 9.2 最大最小分配

建议用等权逐步填充实现交叉资源分配。用 $j$ 统称 A 出口、B 出口和已知目的资源，$\mathcal F_j$ 为成员集，$C_j$ 为预算；初始所有实际分配为零。

```text
U = 有可发送数据、没有明确禁止发送、候选上限为正的流
r = 0
while U 非空:
    delta = min(
        min(cap[f] - r[f] for f in U),
        min((C[j] - sum(r[f] for f in F[j])) / count(U ∩ F[j])
            for j with count(U ∩ F[j]) > 0))
    向 U 中每条流增加 delta
    冻结达到自身 cap 的流
    冻结落在任一已耗尽资源中的其余流
    若因数值误差没有进展，按显式容差处理并结束，不能死循环
```

所有流至少受自己的 A 物理出口限制。预算缺失不能用无穷大假装已知：未确认的远端归属不套用 B 资源预算，但仍受 A 共享出口容量约束，有可靠目的约束时照常叠加。

状态保留不等于带宽预留。无数据流的份额归还，数据到达时触发重新分配；不能把历史有效服务估计因为当前空闲而清零。

### 9.3 分配后检查

最终速率必须重新进入第 8 节的包级或分段轨迹。对超风险资源，收紧会继续增加其风险的流上限，再联合分配；跨出口的目的资源不能漏掉。

收紧方法和最大迭代次数为 D4。**建议**使用有界迭代和明确失败返回：没有通过检查的动作不能提交；停止相关新增注入并记录原因，未受影响资源仍可分配。若已经在途的字节就足以超限，即使新速率归零也要报告“无法撤回的风险”，不能将零速率结果标为已消除风险。

每轮以同一决策版本提交所有执行速率和共享许可。提交前记录最终预测快照，完成批量更新后再唤醒设备，避免某条流先用新份额、其他流仍用旧份额。

## 10. 逐流执行器、满桶与唤醒

### 10.1 现有接口的迁移

现有 `ConfigureInjectionGroup()`、`BindInjectionQueue()`、`ApplyInjectionControls()` 为共享组桶服务。计划应使一个执行状态只属于一条流，资源共享通过预算和许可实现。

**建议的接口契约，不是现有 API：**

| 接口 | 必要语义 |
|---|---|
| `CreateFlowShaper(handle, pg, K)` | 成功创建一次，$z=K$；没有正速率和许可也不发送 |
| `BindFlowQueue(handle, queue_handle)` | 验证两者代际，绑定有限空队列 |
| `ReadShaperSnapshot(handle, now)` | 按旧速率结算至 now 后读取；预测使用副本 |
| `ApplyFlowControls(batch, decision_id)` | 校验全批次、先结算旧速率、再统一更新速率和许可、最后唤醒 |
| `DetachEmptyFlowQueue(handle)` | 非空或仍有出队引用时拒绝；保留余额 |
| `DestroyFlowShaper(handle)` | 仅在生命周期条件满足后销毁，旧唤醒事件不得再操作槽位 |

是否重命名全部现有接口由实现者决定，但不能只是改名后继续让多流共享一个预测桶。逐流处理也不能取消物理总预算。

### 10.2 令牌更新

$$
K_f=4\times\mathrm{frameBytes}_f,\qquad z_f(t_{\mathrm{create}})=K_f.
$$

```text
settle(bucket, now):
    assert now >= updated
    tokens = min(K, tokens + old_rate * seconds(now - updated))
    updated = now

set_rate(bucket, new_rate, now):
    validate new_rate
    settle(bucket, now)
    rate = new_rate
    // 不因 new_rate == 0 清零 tokens

can_send(flow, head):
    return rate > 0
       and tokens >= head.bytes
       and shared_permission_allows(head)
       and not paused(flow.pg)
       and queue_and_history_reservations_valid
```

帧长从设备/协议计量配置取得，允许的完整报文必须放得进桶；非法大包不能永久堵在队首而没有告警。改变 MTU 或计量格式时重新验证容量与存量余额策略，具体运行时重配置属于 D9。按 1048 字节计量帧长，$K_f=4192$ 字节。

真实选包后扣一次令牌。查队首、入队、更新反馈、重复调度均不扣；零速率区间不补充，恢复不重填和追补。PFC 暂停若仍有正速率可以补至满，若实际分配已归零则冻结，均不得发送。

### 10.3 启动额度与共同突发

新流立即获得四帧满桶，候选速率取 A 物理出口容量，经现有共享资源分配器得到可用份额；多个新流的目标总速率不能超过出口及已知目的容量。令牌按份额连续补充，不等待远端许可，也不使用 1% 冷启动速率。

首包成功入队后通过合并的即时事件调用分配路径；普通后续入队仍保留周期控制节奏。B 首包后主动反馈，A 收到有效状态后按反馈控制，陈旧反馈、暂停和历史不足的保护继续生效。

不新增共享启动/恢复许可或额外风险迭代。多个满桶的发送由物理端口串行化，预测沿用实际执行器规则；这不保证未知远端没有启动积压。共享突发与恢复风险仍需验证，不能把四帧额度解释成整个端口只有四帧余额。

### 10.4 调度与唤醒

现有 `BEgressQueue::DequeueRR()` 可以提供候选选择基础。保持队列的 PG 映射用于暂停与 MMU，使用本地队列代际防止复用后旧事件误操作。

不足一个队首包的令牌等待时间为：

$$
\Delta_{\mathrm{token}}=\frac{[\ell-z_f]^+}{r_f},\qquad r_f>0.
$$

向上取整到时间分辨率，并只安排必要的最早唤醒。零速率不除法、不安排无限重试；正速率恢复、许可恢复、入队、发送完成和 PFC resume 都可以合并触发调度。

当前组内游标只在本组成功出队时前进的原则值得保留；逐流桶下不需要旧的组内竞争状态。既有轮询按包选择，不能据此声称变长报文在短窗口内严格字节公平。若研究要求字节公平，可另行采用字节赤字调度，需明确为附加选择和代价。

## 11. 本地 CNP、原生反馈与 PFC

以真实本地缓存范围建立压力统计，不按“B 出口＋PG 控制组”复制整机缓存。统一窗口内测量 $\lambda_A,x_A,Q_A$：

$$
P_A=Q_A+[\lambda_A-x_A]^+\tau_{\mathrm{local}}+M_A,\qquad
0\le Q_L<Q_H<B_A.
$$

计划遵循方案中的触发、响应等待、排空时停止追加、低水位解除和紧急保护。保护状态是资源级，最近通知时间及发送端 QP 映射是逐流的；不能因一个 PG 内少数流造成压力就对全部流发送 CNP。

**建议复用的现有选择规则**：普通反压每个资源响应轮次选一个仍有输入的主要贡献流；结合该 QP 最近原生 CNP 等待其响应，再判断是否追加。紧急情况下可覆盖其他贡献流，但仍满足逐 QP 最小间隔。该具体选择规则应在元数据中写出，不能把它当作 DCQCN 协议要求。

当前源 QP 映射可以从模拟数据的地址、源端口、PG 取得，须与 `RdmaHw::GetQp(ch.sip, fid, pg)` 的语义一致。采用第 4.1 节的三元组后，若仍使用现有端点通知接口，这些字段只能作为独立通知关联属性，不能参与 R5 流查找；切换为 QPN 端点接口时必须一并更新通知构造与接收查找。真实 RoCE 的源 QP 来源是独立信息前提，见 D6；目的 QPN 不能替代它。映射未知时禁止发错误定向 CNP，保留原生反馈和真实 PFC。

所有原生 CNP、带拥塞标记的 ACK 和既有 CE 保持原语义。观察原生通知仅服务记账和减少本地重复反压，不能截断主机反馈。PFC 继续按实际优先级工作，暂停改变可影响服务估计和执行资格，不等于逐流授信变化。

主机恢复参数属于端侧配置，应与对照使用一致的有效值；本轮方案落实不把修改 DCQCN 恢复参数作为隐藏前提。

## 12. 生命周期、回收与耗尽处理

### 12.1 转换条件

建议状态名为 ACTIVE、IDLE、GUARD；无记录不是已知连接结束。

| 转换 | 条件与动作 |
|---|---|
| 无记录 → ACTIVE | 本地真实数据到达且资源事务成功；分配新代际，A 首次满桶 |
| ACTIVE → IDLE | 常规与待处理数据均排空，未完成数据操作为零；记录空闲起点，归还发送份额 |
| IDLE → ACTIVE | 新数据到达；沿用代际、计数和余额，必要时重申请队列 |
| IDLE → GUARD | 空闲至少 $T_{\mathrm{idle}}$；本地无积压/引用；A 在途与远端驻留可核销，B 本地驻留为零；保存小记录 |
| GUARD → ACTIVE/等待资源 | 保护期内新数据；撤销截止，恢复原记录，不满桶重授 |
| GUARD → 无记录 | 保护截止且没有新数据、等待报文和旧操作引用；解除绑定、取消任务、释放身份 |

反馈和周期任务不刷新数据空闲计时。有积压的流不能因没有新到达而老化；长期零速率和 PFC 暂停同样保留。

队列资源可以先于流状态释放，但必须为空、移出调度且没有旧引用。回收时应遵守顺序：使句柄不可再被调度选择，取消或失效旧任务，确认数据引用归零，结算保存余额和基线，最后释放队列或身份槽位。检查代际仍是必要防线，不能只依赖取消定时器成功。

### 12.2 未核销状态和保护记录

$T_{\mathrm{idle}}$、$T_{\mathrm{guard}}$ 与 $F_{\max}$ 各有独立含义。提供可信 $D_{\mathrm{old}}$ 时，检查：

$$
T_{\mathrm{guard}}\ge D_{\mathrm{old}}+F_{\max}+\text{计时余量}.
$$

没有覆盖排队、PFC 和允许重传的失效边界时，不得宣称此不等式已经证明旧包消失。无法核销的在途或远端驻留保留原记录与原因，即使这会阻止接纳新流。

不同 A/B 创建时刻、B 测量重置或丢包可能使计数无法对齐。保留保护记录不能代替正确基线；D8 未解决前，禁止只用“当前 B 出队大于当前 A 发送”判断全部排空。

完全老化后的同键数据重新经过启动分配，记为新控制观测段。真实连接没有线上代际时，不保证同一 QP 终身仅获得一次桶。

### 12.3 耗尽顺序

身份池同时计算 ACTIVE、IDLE、GUARD；保护记录空间建表时预留。A 逻辑队列、等待缓存、历史、预测与控制待处理请求分别有上限。

资源不足按以下顺序处理：

1. 查已有状态；已有资源的流继续运行。
2. 回收安全空队列和已到期保护记录，不驱逐积压或未核销状态。
3. 进入固定大小的等待区；只在资源变化或有界重试事件中检查。
4. 同流保持顺序，暂不可接纳的流不阻塞已具备资源的其他流。
5. 等待区满或超过 $T_{\mathrm{pending}}$ 则丢弃，分别记录身份、队列、历史、缓存和超时原因。
6. B 的资源不足通过有界资源反馈告知 A；A 限制相应未确认启动流，恢复通知丢失时仍有有界探测。

未知身份的拒绝用端口/原因累计计数，不能为了记录每个失败身份另建无限表。队列、历史和反馈的操作引用也要有界。

历史池不足时只淘汰不再被有效重放需要的记录；超期校验标记缺失。没有空间记录下一次真实发送时停止相关 WAN 出队，并由本地缓存反压约束输入，不能靠漏日志继续宣称预测有效。

### 12.4 标识与路径变化

有可信真实连接代际时，新旧连接可分别关联，但旧积压和在途仍独立处理，两代均占用有限资源。没有这种信息时，相同键命中保留记录就继续使用，不靠包序号猜测重建。

路径或 PG 属性冲突必须使原关联的适用性重新检查。**建议**基础实现先明确拒绝不支持的动态迁移并记原因；完整迁移需要队列顺序、旧路径在途和新测量基线协议，属于 D8，不能由一次本地重新查路由自动解决。

### 13.3 启动与运行约束

- 所有主机地址全局唯一，每个 Leaf 有独立的 `/24`，其主机与接入端口地址互不重复；各地址池和网关控制地址互不冲突。每台主机恰有一个非回环接口 IP，与 `serverAddress` 及 IP 映射一致。拒绝地址池耗尽、不支持的多接入和无法确定 DC/Leaf 归属的拓扑。
- R5 受控数据必须能够解析目的 QPN，发包、收包、网关和日志采用一致的三元组定义；不能用隐式 Tag 或端口键掩盖报文支持缺失。
- 时间、容量与资源上限为有限合法值，计量字节口径一致。
- 支持候选反解的路径有 $L>0$；理想模型的 $\Delta_c/L$ 检查不能冒充完整稳定性证明。
- 桶能容纳最大允许数据包，队列槽位上限不超过底层实际可用数量。
- 队列目标、风险余量、等待区和保留缓存共同受真实池容量限制。
- 已配置正向/控制路径，不依赖未来流才能启动；没有流时也能正确处理控制与老化任务。
- 不要求控制周期与反馈周期必须整除，除非实现明确选择这种调度限制并在配置检查中说明；原有取模逻辑需相应处理。
- 源码默认值不自动满足延长后的历史与预测校验窗口。保留期不足必须报配置问题或标记覆盖不足，不能偷偷获取已删除数据。

日志应能串起“观测—决策—实际发送—结果”。文件名可以调整，但格式版本、字段单位和关联键要明确。

| 记录 | 必须回答的问题 |

| B 数据事件 | 实际入口/出口/队列、成功入队、出队、各类丢弃、驻留与累计边界 |
| 反馈 | 发送/到达时间、采样时间、年龄、会话/代际/样本序号、接受或拒绝原因 |

| 决策 | $t,s,h,F,L$、候选上限、最终分配、桶余额、许可、供给/服务假设、峰值、风险原因、迭代结果 |
| 校验 | 冻结预测与实际输入重放分开，比较时刻、误差、计划偏差、历史覆盖和缺失原因 |
| 本地反压 | $Q_A,\lambda_A,x_A,P_A$、贡献流、普通/紧急原因、最近本地/原生 CNP、等待与解除 |

时间相同的事件使用单调本地事件序号记录顺序；本地序号不作为对端可见事实。A/B 日志通过 FlowKey、双端控制代际和实际关联匹配，不能继续用相同实验 FlowID 直接连接。

当前 `verify-longhaul-r5.py` 假设组桶一帧、初值零、零速率清零，以及 A/B 流 ID 相同；这些规则必须按新日志版本更新。当前 `analyze-longhaul.py` 的 `r5_evidence()` 也读取组日志，不能直接解释新逐流数据。

验证口径至少覆盖：主机 TX payload/wire、A 实际 WAN 发送、B 出队、接收唯一 goodput、完成与残留、真实丢弃、PFC 暂停区间。每流与聚合指标、目标速率与实际吞吐分开。

## 15. 按依赖实施与验收

以下为后续代码工作的顺序，不表示本次文档整理已经实施或运行这些检查。

| 步骤 | 工作 | 完成标准 |
|---|---|---|
| 1. 地址与身份契约 | 落实三元组 FlowKey、单主机 IP 地址计划与路由映射；明确端点 QPN/源 QP 通知、报文格式，再确定时间计量、服务分摊、共享容量分配、准入和基线等待决项 | 地址不重叠且每主机仅一个接口 IP；目的 QPN 真实随包传递，无网关预注册；接口、格式与单位无冲突 |
| 2. 空表装配与发现 | 改 Setup/Start，增加准入事务、有限身份/队列池、A/B 独立首包事件 | 初始化空表；首包不直通、不漏计；未来未发流不影响当前控制 |
| 3. 生命周期与执行器 | 逐流四帧满桶、零速率余额、队列复用、等待与资源失败、代际校验 | 保留窗口内不重复授信；积压不老化；所有池有硬上限；释放无旧引用 |
| 4. B 观测和关联 | 逐流/资源测量、新消息、会话与关联、状态变化反馈 | A 不创建 B 状态；重复/旧反馈不回滚；无数据时仍能恢复反馈 |
| 5. 历史与完整 RTT 预测 | 真实发送提交、时间映射、未来供给/令牌/调度、共享峰值、冻结校验 | 不提前发送未来供给；不撤回在途；正常与风险模型注明假设 |
| 6. 联合分配和反压 | 候选与份额分离、交叉资源分配、最终复核、定向本地 CNP | 从空闲零份额可恢复；实际执行与预测一致；保留原生 CE/CNP |
| 7. 日志与回归适配 | 更新现有机制测试、审计器、元数据和分析格式 | 能从原始事件闭合字节/令牌/池占用，并区分新旧运行格式 |

每一步优先核对机制不变量，再做相关测试；不为文档拆分运行实验。后续验证可围绕以下必要边界：

- 两个 DC 的主机、接入接口、交换机间接口和网关控制地址均无冲突；同 Leaf 主机共用 `/24`，不同 Leaf 前缀不同。地址计划不随工作负载改变，主机接口与 RDMA/路由/统计使用同一 IP。
- 同 Leaf、同 DC 跨 Leaf、跨 DC 的两个方向均按精确主机路由选择正确出口；不把共享前缀当作共享物理链路，也不依赖普通全局路由修正错误表项。
- 两个方向的数据、ACK/CNP 和网关反馈均可达，PFC 取发送接口地址；基线与 Proposed 使用相同地址和报文口径。
- 同一 IP 对的不同目的 QPN 分流；相同三元组不因端口或 PG 变化重复授信，属性变化按关联规则处理；QPN 缺失、冲突、耗尽和重用均有明确结果。
- 若最终完整帧为 1048 字节，满桶为 4192 字节；加入目的 QPN 后按实际新头长重新计算，变长包按实际大小消费。
- 零速率期间余额保持且无发送，恢复不补算；PFC 下正速率与零速率分开检查。
- A/B 首包创建时机、第一次成功准入与第一次实际发送顺序正确。
- 保护期前后再来包、反馈心跳、重复反馈、旧会话、计数重置和队列槽位复用。
- 各资源池分别耗尽；等待重试不乱序、不重复 MMU 扣账，控制反馈与已有流可继续排空。
- $t+d_b$ 之后的 A 发送不进入 B 的 $t+T$ 队列；峰值在终点之前发生时也受保护。
- 服务暂停/恢复、曾经排空、供给变化与残差归因不混淆。
- 多 B 出口汇聚同一目的、不同 PG 共用出口、同 PG 不同流的控制粒度正确。
- 近端 CNP 等待响应、明确排空后不追加、紧急保护和原生反馈透传。
- 若支持丢包/重路由，计数与历史缺口必须显式处理；未支持的范围不能用无损断言掩盖。

性能实验在机制闭合后另行安排，使用与 DCQCN 匹配的负载、窗口、缓存和信息权限；测试通过也不等于已经证明吞吐优势。

D8 尤其需要提前解决：A 重建了控制记录而 B 仍保留旧累计值时，直接令两边计数从“当前值”重新相减可能遗漏已经到达的本段数据。可以研究在可证明排空且旧数据失效后建立共同检查点，或通过受管理 WAN 的真实封装传递控制代际/发送序号。后者会增加报文格式和开销，属于补充设计，尚未纳入基础数据格式；不能以模拟器隐式 Tag 替代论证。未建立可信基线时，允许使用有效队列采样及可覆盖历史做有条件预测，但不能声称已完成累计守恒核销。

方案中的三元组流身份、全局唯一且每主机一个非回环 IP、A/B 职责、真实发送历史、$F=t+T$、四帧满桶、零速率保留且停发、首包独立建表以及有限资源规则不属于这些待决项。待决的是落实它们的具体策略和参数，不应在编码时静默改变机制定义。


## 针对16节问题的决策
D1：时延参数采用运行时测量
$d_f$、$d_b$ 和 $\tau_{\mathrm{local}}$ 在运行过程中测量并更新，不再按未来流列表预填。
需要明确测量边界：从哪个发送事件到哪个接收/入队事件，以及序列化、接收处理是否已包含，避免重复计算。测量尚未有效时使用明确的保守初值。

D2：B 负责观测，A 负责控制
B 不新增逐流限速或公平调度机制，保留实际 PG/FIFO 调度，只观测队列、出队、暂停及服务能力；A 根据反馈分配并执行发送速率。
需要区分：B 测得的逐流出队速率是近期服务结果，不是未来保证份额。 A 的公平分配也不能直接当成 B 的实际服务能力。逐流服务预测和 $q_f^\star$ 的取法仍需随预测模型细化，但不要求 B 为此增加控制机制。

D3：在 A 实现基于实际发送历史的完整 RTT 预测
采用 Smith Predictor 的时延补偿思路，定义当前决策时刻为 $t$，预测终点为：
$
F=t+T,\qquad T=d_f+d_b.
$
基本流程：
1. 从 B 在采样时刻 $s$ 的真实队列出发。
2. 将 A 的实际发送历史按正向时延映射为 B 的到达事件，补偿旧采样到当前状态之间的变化。
3. 从当前时刻起，结合 A 当前积压、近期入口供给估计、候选速率及实际发送约束，推演未来发送。
4. 将这些发送映射到 B，与服务估计一起分段计算队列，得到终点队列和途中峰值。
5. 根据预测调整候选速率；后续反馈返回时校验预测误差。
这里有两个关键边界：
- 新动作最早在 $t+\delta_a+d_f$ 影响 B，之前的在途数据不能被新动作撤回。
- 固定时延下，只有 A 在 $F-d_f=t+d_b$ 之前发出的数据能进入预测终点。
未来供给和服务变化属于估计，不能当作已知事实；队列排空、暂停/恢复等事件需要分段处理。不读取未来应用发送计划，也不把目标速率直接当成实际发送量。

D4：暂不新增机制
本轮不设计共享启动/恢复许可、额外的风险收紧迭代机制。预测仍需遵守实际执行器已有的约束，并记录队列峰值；不能据此宣称已经解决多流同步突发问题。

D5：控制报文采用流身份与资源身份分离的设计
不把 PG 作为流身份或每条流反馈的必填字段。建议保留以下内容：
类别	建议字段
格式与顺序	版本、消息类型、长度/记录数、会话标识、消息序号
流身份	FlowKey、连接代际
资源关联	B 分配的资源 ID、关联版本
采样与计数	SAMPLE、QUEUE、ARRIVED、DEPARTED、DROPPED
服务与缓存	SERVICE、BACKGROUND、CAPACITY、BUFFER
有效性	服务估计是否有效、是否暂停、采样区间是否曾排空

其中，资源 ID 用来让 A 知道哪些流共享同一资源，B 内部自行将其映射到端口/PG，不必直接反馈 PG。
逐流计数与资源级计数应明确区分；共享资源的服务能力、背景流量和缓存信息不能被各流重复累加。登记/关联消息需要确认和有限重试；周期状态反馈采用新状态覆盖旧状态、序号去重和超时失效。具体编码、批量上限及重试参数后续确定。

D6：简化建链登记，首包建立控制状态
保留：
FlowKey = (Src IP, Dst IP, BTH.DestQP)
两端创建 QP 并交换 QPN；源端向 A 发送登记报文，建立：
FlowKey → SrcQP、连接代际
A 确认关联后才允许主动 CNP。数据首包独立触发控制状态创建；登记不提供未来流大小、启动时间或需求。

D7、D8、D9 暂缓。


标准 RDMA 本身具备、但当前仿真缺失的必要能力，如 QPN 分配、端点 QPN 交换、报文编码与 QP 查找，放在 RdmaHw 及相关 RDMA 模块中实现；Longhaul/R5 特有的机制，如向网关登记源 QP 关联，放在 Longhaul程序或R5 模块中实现。仅补充方案必需的能力，不扩展为完整 RDMA 协议栈。
