# 跨数据中心拥塞控制：第一版实验报告

日期：2026-09-17。状态：已完成最小实现、18 次完整运行、2 次冒烟运行及统计核验。实验为单种子初步结果，不给置信区间，不代表生产网或论文原始实现的普遍性能。

**汇报要点：长距竞争场景出现深队列、准入丢包和有效吞吐下降；近源虚拟队列/CNP 显著缓解这些现象。当前接收预测器的独立收益未得到证实，不能把组合方案的收益全部归功于预测。**

## 1. 背景与问题

研究场景为跨 DC RDMA 传输，源主机经 200Gbps、单向5ms的长链路到达接收 DC，并竞争一个100Gbps接收出口。新流加入后，远端出口不能立即要求在途数据减少；源端调速动作和数据传播也需要时间。

本轮优先回答：反馈/执行环路较长时，已有控制是否能在有限缓存中抑制过载；近源执行能否缓解；接收侧预测是否在近源执行之上提供独立收益。

## 2. Baseline 与实际观察

DCQCN 使用 ECN/CNP 驱动降速和恢复，本文采用仓库已有实现；HPCC 使用 INT 链路遥测，TIMELY 使用 RTT/RTT梯度。HPCC 的原论文已讨论延迟遥测与过度反应，不能把“考虑反馈延迟”本身宣称为新机制。[DCQCN 作者页面](https://haggaie.github.io/publications/2015-dcqcn)、[HPCC 原论文](https://minlanyu.seas.harvard.edu/writeup/sigcomm19.pdf)、[TIMELY 作者机构页面](https://research.google/pubs/timely-rtt-based-congestion-control-for-the-datacenter/)。

先核验单流长距传输，最后30ms结果如下；均无接收出口排队和准入丢包，说明当前小拓扑可正常传输：

| 算法 | 稳态有效吞吐 Gbps | 队列峰值 MB | 准入丢包 |
|---|---:|---:|---:|
| dcqcn | 96.39 | 0.00 | 0 |
| hpcc | 86.74 | 0.00 | 0 |
| timely | 90.02 | 0.00 | 0 |

这些单流差异包含算法参数、INT/时间戳报头开销和控制行为，不能仅凭此表推断算法优劣。

### 流加入场景的主要结果

10ms开始1条长流，50ms另外3条加入，均发往同一接收出口。每条2GB，180ms仿真内均未完成。主要统计窗为(50,170]ms；稳态窗为(140,170]ms。

| 算法/方案 | 接收队列峰值 MB | 平均有效吞吐 Gbps | 尾窗有效吞吐 Gbps | 全程准入丢包/包 | 尾窗 Jain | 收敛 |
|---|---:|---:|---:|---:|---:|---|
| dcqcn | 52.43 | 24.51 | 18.19 | 623,431 | 0.9997 | 未收敛 |
| hpcc | 52.43 | 7.88 | 2.86 | 646,994 | 0.8994 | 未收敛 |
| timely | 52.43 | 6.80 | 0.72 | 692,923 | 0.9175 | 未收敛 |
| reactive-cnp | 6.18 | 62.32 | 64.09 | 0 | 1.0000 | 未收敛 |
| predictive-cnp | 6.18 | 62.32 | 64.09 | 0 | 1.0000 | 未收敛 |

![流加入场景：队列、发送、到达、离开、虚拟队列和丢包](../results/research-20260917/pilot/figures/join-overview.png)

原 DCQCN 的队列峰值52.43MB，接近配置的50MiB出口池上限；其余 baseline 也反复达到该上限，发生数十万次准入丢包。有效吞吐显著低于出口离开速率，符合重复/乱序流量占用链路而不形成新有效字节的现象；本轮没有单独统计全部重传包数，不能给出精确重传比例。

近源组合相对 DCQCN：峰值从52.43MB降到6.18MB（约下降88.2%），有效吞吐从24.51提升到62.32Gbps（约2.54倍），准入丢包计数由623,431降为0。Jain接近1只能说明分配接近公平，并不说明链路得到充分利用；近源组合仍有明显吞吐空洞，所有方案都没有达到本报告的持续公平速率收敛标准。

## 3. 问题原因分析

因果链：新流加入 → 接收到达速率暂时超过100Gbps出口能力 → 队列累积并触发ECN/PFC → 跨域反馈仍在返回途中 → 旧发送行为继续到达 → 缓存准入丢包 → 乱序/重传与后续降速使有效吞吐恶化 → 发送与恢复反复波动。

数量级解释：假设200Gbps到达、100Gbps排出，10ms反馈与数据往返时间内可积累约125MB额外数据，超过50MiB出口池。这个计算是过载持续时的解释模型，不是实测125MB队列，也不是不可避免的下界；实际速率、PFC、源队列和控制会改变积累量。

### 延迟成对核验

只改变 WAN 单向延迟为5ms或5µs，二者均关闭发送窗口，其余 DCQCN 配置和流量相同：

| 单向延迟 | 队列峰值 MB | 有效吞吐 Gbps | 准入丢包/包 |
|---|---:|---:|---:|
| 5 ms | 52.43 | 23.11 | 636,881 |
| 5 µs | 1.02 | 85.71 | 0 |

这一对照支持“当前配置下，长反馈环路使竞争更难控制”。它不能把全部差异拆分为反馈过时、PFC、重传或恢复各自的贡献：程序还会按链路延迟计算headroom，RTT派生状态也随之变化。

另有保留发送窗口的短延迟对照，但窗口随基础RTT缩小，吞吐受窗口约束（约61.1Gbps），因此不把那组当作纯反馈延迟证据。没有为让 baseline 表现更差而单独改变其 buffer、流量或ECN。

## 4. 新方案设计

完整初稿见[方案v0.5实验草案](拥塞控制方案v0.5-实验草案.md)。已实现三部分：

1. 接收DCI每1ms读取真实出口队列和延迟送达的实际跨域发送统计，计算组目标。
2. 发送DCI每100µs按 `z=max(0,z+Din−u·δ)` 更新虚拟队列，并向实测速率超过组公平目标5%的活跃流发近源CNP。高/低阈值为1MB/0.25MB，初始组目标为已知100Gbps出口能力。
3. RNIC使用原DCQCN降速和恢复机制。近源CNP为实际报文；原端到端ACK/ECN路径仍保留。

预测最小模型：以经过5ms传来的源DCI实际出口速率a估计当前到达率，`q_hat=max(0,q+(a−C)H)`；H取名义10.033ms。目标 `u=clip(C−(q_control−1MB)/H, N×100Mb/s, 0.98C)`，本式速率上限/下限在代码中统一换算为字节/秒。reactive-cnp使用q，predictive-cnp使用q_hat。目标经过5ms后登记到发送DCI。

这里的预测是零阶速率外推，尚无目标执行时间辨识、未来控制轨迹重放或残差学习。H不包含所有排队和DCQCN动态，不能称为已测得的完整控制时延。

### 预测消融：当前不支持独立收益

流加入场景中，两种近源版本的队列、有效吞吐、CNP发送数（167）完全一致，尽管接收目标轨迹不同。说明当前目标变化没有改变执行结果；可能与CNP门控死区和底层控制动态有关，这一原因尚未被进一步隔离验证。

![预测队列与实际队列、目标和源端执行目标](../results/research-20260917/pilot/figures/join-predictive-cnp-control.png)

预测曲线在首次突发时明显高估后续队列，不能包装成准确预测。当前较有把握的收益来自近源执行及预配置容量约束；预测器本身仍需改进和独立验证。

## 5. 实验设置与指标口径

| 项目 | 设置 |
|---|---|
| 仿真器 | 当前工作区 ns-3.39 / PowerTCP派生实现，源码及diff已留存 |
| 核心拓扑 | 10节点：两台DCI、每侧4台主机；9链路；无ECMP路径歧义 |
| 速率与时延 | 主机口100Gbps/1.5µs；DCI口200Gbps/5ms；NIC处理15µs |
| 基础RTT | 元数据10.0062ms，不含全部NIC处理/排队；不是实测RTT分布 |
| 数据包 | 1000字节载荷；DCQCN/HPCC/TIMELY有不同固有报头 |
| buffer | 基础pool和出口lossless池50MiB；另按各端口速率×传播延迟×3分配每优先级headroom，不能称总buffer只有50MiB |
| ECN | 100Gbps口Kmin400KB/Kmax1600KB/pmax0.2；200Gbps口800KB/3200KB/0.2 |
| 端侧参数 | 共用config-longhaul-common.txt；DCQCN RP_TIMER=900µs、AI=50Mb/s、HAI=100Mb/s；HPCC目标0.95；TIMELY阈值5/10ms |
| 随机性 | seed=1/run=1，每配置一次；无置信区间 |
| 采样 | 发送/接收100µs，接收出口/控制状态1ms |
| 主比较 | dcqcn、hpcc、timely、reactive-cnp、predictive-cnp；同拓扑/输入/窗口/ECN/PFC/stop |

队列使用明确的接收DCI9→主机4出口，按数据包入队和出队分别计字节；已验证每条记录 `累计入队−累计出队=当前队列`。1ms采样峰值可能漏掉更短峰值。源实际线速TX通过RNIC数据包出队trace计量；它与 `snd_nxt` 进度差分分开。有效吞吐为接收端按序有效字节，采样器略去首次不足100µs的接收片段；有限流累计积分约399.375MB，而真实完成总量400MB，相差约0.16%。FCT使用完成事件，不受该积分误差影响。

收敛使用1ms有效吞吐分箱，每条活跃长流达到报头修正后的100Gbps/N有效载荷公平份额±10%，持续至少3×基础RTT（向上取整31个箱）；必须整组满足。DCQCN公平目标约23.85Gbps/流，HPCC约22.94，TIMELY约23.67。当前数据全部未满足，不能声称已缩短满速收敛时间。

Jain使用最后30ms每条长流的平均有效吞吐，缺失补零。有限流完成后的空闲区间不报告Jain。ECN为接收瓶颈出队时已有ECN标记的数据包数，不声称全部标记都在该处首次产生。丢包为所有交换机准入拒绝次数，重传再次拒绝会再次计数；不等同于独特丢失序号数量。随机链路错误关闭。未采集实测RTT分布，不能用基础RTT冒充；也不输出未经测量的真实RTT改善率。

## 7. 实现与可靠性检查

- 最小逻辑放在 `longhaul-research.h`，入口增加3个研究CLI参数。底层只补独立CNP处理和交换机准入丢包计数。
- 发现原1TB流量触发 `GetBytesLeft()` 先缩为uint32再取MTU的问题：发送约3,567,587,328字节后低32位为零，可能不断生成零载荷包。原大拓扑运行已停止并标记INVALID，未纳入上述结论。核心实验每流≤2GB，避免该路径和32位序号回绕；本轮不重构运输层序号语义。
- 原 `dci-link.csv` 的rx_bps来自出口方向累计进入字节，不能解释为该链路入站接收速率。新报告用独立出口入队/出队trace。
- 独立CNP接收函数原先未触发DCQCN降速；已补调用，并忽略流完成后的迟到CNP。原baseline仍按原ACK拥塞标记处理。
- 共18次完整运行退出码为0，2次短冒烟通过；主要5算法配置一致性、队列字节守恒、遥测时间因果性核验通过。结果证据见[validation.json](../results/research-20260917/evidence/validation.json)。
- 原工作区已有修改已保留，起始diff、输入、有效配置、运行命令、源码快照和hash均留存。新方案CSV中的algorithm仍标底层dcqcn，具体变体以目录、run.json及metadata.research_control为准。

## 8. 当前结论与下一步

**已验证：** 本仓库当前配置下，长距竞争会产生深队列与大量准入丢包；近源虚拟队列/CNP改善队列、有效吞吐和有限流完成情况；当前预测消融没有显示稳定的额外收益。

**解释模型/推测：** 传播反馈滞后造成的过载持续时间与缓存预算不匹配是重要原因；PFC、重传与恢复共同放大损失；CNP门控死区可能掩盖远端目标差异。尚未拆分它们的贡献。

**尚未验证：** 精确预测、稳定性证明、未知可用容量估计、复杂拓扑与多组公平性、短流尾部统计、种子稳定性和真实协议开销。当前方案仍有明显吞吐损失，不是成熟算法。

下一轮P0建议：先记录目标登记→CNP→实际速率变化的执行时延与状态，确认预测目标能够改变实际动作；再在接收DCI本地竞争导致容量突变的场景验证预测。不要优先做大规模参数搜索，也不要为得到正面结果隐藏当前消融。
