# 接收侧预测控制与近源 CNP 执行：方案与初步实验报告

2026 年 9 月 17 日

本报告在 [拥塞控制方案 v0.4](拥塞控制方案v0.4.md) 的基础上，介绍方案的初步实现和实验结果。仿真沿用 `crossDC-evaluation-workload.cc`，重点考察接收侧控制与近源 CNP 在跨数据中心拥塞场景中的作用。

初步结果表明，在当前实验配置下，所提方案（下文记为 proposed）能够降低突发 incast 的流完成时间和准入丢包次数，但队列峰值没有改善。预测项的作用尚不明显，流数量减少后的速率恢复也比较慢。

## 一、核心思路

本方案将控制点放在接收侧 DCI。接收侧根据瓶颈队列、链路容量和发送侧的实际流量，计算流组的目标速率，并反馈给发送侧 DCI。发送侧维护虚拟队列，在流量超过目标时向 RNIC 发送近源 CNP。

接收侧和发送侧采用不同的控制周期。接收侧以较长周期更新聚合目标速率，并估计反馈生效前的队列变化；发送侧以较短周期检查实际注入量，对超过目标份额的流发送 CNP。这样，跨域反馈负责调整总体发送能力，近源反馈负责推动 RNIC 执行。

由于 RNIC 调速需要时间，目标速率与实际发送速率之间可能存在差异。因此，方案使用实际发送量估计后续到达流量，而不直接假设目标已经生效。v0.4 中还考虑了利用预测误差进行校准；当前实现暂时采用简化预测，执行延迟估计和误差校准留待后续完成。

## 二、研究动机与问题分析

### 2.1 场景与问题

实验采用跨域长链路连接两侧 DCI，多个发送端竞争接收侧出口。跨域单向传播时延为 1 ms，跨域链路为 100 Gbps，接收侧瓶颈为 50 Gbps。突发流到来时，输入能力可以显著超过接收侧服务能力。

拥塞控制的实际作用过程为：

> 接收侧队列增长 → 生成反馈 → 反馈跨域返回 → 发送侧执行 → RNIC 逐步降速 → 新的发送行为跨域到达 → 接收侧队列变化。

即使反馈目标合理，在该过程结束前，旧发送行为和在途数据仍会影响队列。例如，在跨域链路持续输入 100 Gbps、瓶颈服务 50 Gbps 的理想化情况下，2 ms 内的净积压可达约 12.5 MB。这一估算说明，毫秒级的反馈延迟已经足以产生较大的积压，实际队列峰值还会受到调速过程和流量变化的影响。

### 2.2 已观察到的现象

- 8→1 incast 中，当前 DCQCN 的接收侧队列峰值为 21.38 MB，FCT 中位数为 66.46 ms，并产生大量准入丢包。
- 加入 proposed 控制后，FCT 降至 43.58 ms、准入丢包显著减少，但队列峰值仍为 21.75 MB。
- 动态减流后，proposed 末段 goodput 约 17.78 Gbps，低于瓶颈可提供的能力，说明拥塞缓解后仍存在带宽利用不足的问题。

本研究主要关注两个相互关联的问题：一是控制指令与实际发送行为之间的时延如何影响队列预测；二是减少积压后，如何使发送速率及时恢复。

除反馈延迟外，PFC、端侧参数、丢包重传和窗口配置也会影响上述结果。后续需要结合控制日志和消融实验分析各因素的作用。

### 2.3 基线算法的适用性

DCQCN、HPCC、TIMELY 分别使用当前仓库已有的 ECN、INT 和 RTT 控制路径。此次比较固定网络与流量条件，沿用现有主要参数，没有针对每种算法进行充分调优。

HPCC、TIMELY 在 incast 中未完成流，动态场景 goodput 也很低。这部分结果可能与参数不适合长 RTT 场景有关，尚不能据此评价算法本身。例如，代码中的 TIMELY 默认 RTT 阈值为 50 µs / 500 µs，均低于本实验约 2 ms 的传播 RTT，参数适配需要复核。HPCC 的窗口、INT、PFC 与重传交互也需要排查。

## 三、方案框架

```mermaid
flowchart LR
    A[发送端 RNIC] -->|数据| B[发送侧 DCI]
    B -->|跨域数据链路| C[接收侧 DCI]
    C -->|瓶颈出口| D[接收端]
    C -.聚合目标速率.-> B
    B -.近源 CNP.-> A
    B -.实际出口速率及时间戳.-> C
```

| 模块 | 状态与职责 | 当前实现 |
|---|---|---|
| 发送端 RNIC | 执行降速和恢复 | 复用 DCQCN；近源 CNP 触发其原有降速路径 |
| 发送侧 DCI | 统计组内注入、活跃流和实际跨域出口字节；维护虚拟队列 | 每 50 µs 更新虚拟队列，按条件发送真实 CNP 包 |
| 接收侧 DCI | 测量出口队列和链路容量，接收远端遥测，计算聚合目标 | 每 200 µs 更新目标，使用固定时域的零阶预测 |
| 跨域反馈 | 传递目标与遥测 | 通过显式延迟仿真事件传递，当前未封装成网络控制报文 |

当前实现只处理一个接收瓶颈对应的流组，发送主机直接连接源侧 DCI。扩展到多个端口或流组时，需要分别维护控制状态。

## 四、实现细节

实现复用 [现有 workload 入口](../simulator/ns-3.39/examples/PowerTCP/crossDC-evaluation-workload.cc)、[控制实现](../simulator/ns-3.39/examples/PowerTCP/longhaul-research.h) 和 [原有运行脚本](../run_scripts/run_single_workload_algo.py)。

以下公式统一采用字节、秒、字节/秒；报告表格中的速率再换算为 Gbps。

### 4.1 近源虚拟队列和 CNP

每个近源周期 δ，统计进入源侧 DCI、属于目标流组的字节数 D_in，以接收到的聚合目标速率 u 作为虚拟服务速率：

$$z_{k+1}=\max(0,z_k+D_{in,k}-u_k\delta).$$

其中，u_kδ 表示一个周期内的虚拟服务量。相比 v0.4，这里补上了速率与周期的乘积，使公式中的各项均以字节计。

当前反馈条件为：

1. z > z_ref 时开启近源通知；z < z_ref/4 时停止通知，形成滞回。
2. 仅当某流实测速率超过 `(1 + 0.05) × u / 活跃流数` 时向该流发送 CNP，避免对已低于目标份额的流继续降速。
3. 活跃流数下降时，将虚拟积压限制到不超过 z_ref，减轻已退出流遗留的积压影响。
4. CNP 经真实近源链路发往 RNIC；停止 CNP 后，由 DCQCN 自身的恢复机制提速。

这种方式的局限在于，CNP 只能触发降速，提速仍依赖 DCQCN 的恢复过程。即使目标速率已经提高，RNIC 也可能较长时间处于低速状态。此外，当前通过短时间内是否收到数据判断流的活跃状态，可能将暂停或暂时低速的流误判为退出。

### 4.2 接收侧观测与预测

接收侧记录真实出口队列 q、入口/出口字节量和瓶颈容量 C。发送侧记录实际跨域出口速率 a_s，并附采样时间戳，延迟 d_f 后送达接收侧。

当前预测为：

$$\hat q(t+H)=\max\{0,q(t)+w[\tilde a_s(t)-C]H\},\quad w=0.5.$$

其中，ã_s(t) 为接收侧最近获得的发送速率观测。预测假设该速率在 H 内保持不变，并用固定权重 w 减小外推幅度。当前 w 取 0.5，尚未根据预测误差自适应调整。

当前采用固定的预测时长：

$$H=2d_f+2d_{NIC}+3\ \mu s=2.033\ ms.$$

该取值根据传播时延和 NIC delay 配置确定，尚未包含对执行延迟 d₀ 的在线估计。控制周期相位、PFC 暂停和 RNIC 逐步调速都会改变实际响应时间，因此固定 H 可能存在偏差。

### 4.3 目标速率与限幅

以 N 表示接收侧近期观察到的流数，当前目标为：

$$u_{raw}=\max\left\{N r_{min},\ \min\left[0.98C,\ C-\frac{q_{ctrl}-q_{ref}}{H}\right]\right\}.$$

预测版取 q_ctrl = q̂；关闭预测的对照版取 q_ctrl = q。r_min 对应每流 100 Mbps。当前小规模实验中，下界低于聚合上界。

已实现的保护包括：

- 遥测数据距采样时刻的时间超过 `d_f + 2T` 时回退到真实队列控制。
- 聚合目标每周期最多增加 `0.1C`，降速不施加同样的变化幅度限制。
- 目标速率上限为 `0.98C`，队列预测值不小于零。
- 虚拟队列通知使用滞回及 5% 超额门限。

这些限制用于减小目标速率的突变，但实际速率仍取决于 RNIC 的响应。参数目前按初步实验设置，后续还需检查其对振荡和恢复速度的影响；控制稳定性也有待进一步分析。

### 4.4 与 v0.4 的对应关系

| v0.4 的设计 | 当前状态 |
|---|---|
| 接收侧 DCI 作为控制点 | 已实现 |
| 近源虚拟队列及 CNP | 已实现，RNIC 仍使用 DCQCN |
| 实际发送字节和时间戳 | 已实现采样及延迟遥测 |
| 按端口/流组反馈目标 | 当前固定一个流组，未实现通用报文字段 |
| 估计 d_b + d₀ + d_f | 仅使用固定名义 H，未辨识 d₀ |
| 根据到达量预测队列 | 已实现零阶速率外推 |
| 使用预测误差 E 校准 | 尚未实现 |
| 启动、稳态、拥塞阶段区分 | 尚无显式状态机 |

与 v0.4 相比，当前实现主要缺少执行延迟估计和预测误差校准。这两部分是后续完善预测控制的重点。

| 传播 RTT | 约 2.006 ms，不含 NIC、序列化和排队 |
| NIC delay 配置 | 15 µs |
| 交换机 buffer 配置 | 27 MiB，即 28.311552 MB；不是单独为瓶颈队列预留的独享空间 |
| 数据载荷 | 1000 B；不同算法报头开销不同 |
| 背景流 / 网关 | 关闭 |
| 窗口 | `HAS_WIN=0`、`VAR_WIN=0`，六算法一致 |
| 链路随机误码 | 0 |
| 随机种子 | 7，当前仅单次运行 |
| 指标采样周期 | 100 µs；控制日志 200 µs |
| ECN 阈值配置 | 50G：Kmin=200、Kmax=800；100G：400、1600；沿用原配置单位，Pmax=0.2 |

完整参数见 [快速配置](../simulator/ns-3.39/examples/PowerTCP/config-quick.txt) 及结果目录内各次运行的 `config.txt`。其中 DCQCN 沿用 `RP_TIMER=900`、`RATE_AI=50Mb/s`、`RATE_HAI=100Mb/s` 等设置。

Proposed 参数：T=200 µs，δ=50 µs，q_ref=z_ref=250000 B，预测权重 0.5，利用率上限 0.98，超额门限 5%，目标每周期最大增加 0.1C。

### 5.2 实验场景

| 场景 | 流量设置 | 仿真结束 | 主要用途 |
|---|---|---|---|
| basic | 2 流，每流 20 MB，3 ms 同时开始 | 50 ms | 运行正确性、基本队列与 FCT |
| incast | 8 流，每流 20 MB，10 ms 同时开始 | 80 ms | 突发竞争、队列峰值、丢包、FCT |
| dynamic | 2 流在 3 ms 开始，另 6 流在 20 ms 加入，45 ms 停止这 6 流的新数据注入；每流配置 2 GB | 80 ms | 增流响应与减流恢复 |

dynamic 的“减流”指停止新注入，已发送数据仍可排空或重传，接收侧不会在 45 ms 瞬间变为两流。中途截断流不计正常 FCT；该场景不用于比较 FCT。

### 5.3 算法实现范围

| 算法 | 接入与范围 |
|---|---|
| DCQCN / HPCC / TIMELY | 现有 mode 1 / 3 / 7；未进行全面参数适配 |
| Bifrost | mode 12；在已有实现上补动态暂停与暂停到期恢复，参考所提供 ICNP 2023 论文的虚拟状态/授信思想；仅指定入口和优先级，端侧保留 DCQCN，暂停时间量化为 µs，属于简化组合版本，非完整论文复现 |
| FRP | mode 13，仓库已有实现；本阶段作为可运行对照，不展开机制优化或论文一致性论证 |
| Proposed | mode 1 加接收侧控制和真实近源 CNP；跨域遥测/目标用延迟事件模拟，不计控制报文带宽竞争、丢失和乱序 |

全部算法使用相同的拓扑、流量文件、buffer、停止时间和指标代码。共同使用修正后的 PFC 到期恢复逻辑，因此本报告结果不能直接与修正前旧批次混合。

### 5.4 指标定义与数据检查

- TX Rate：从实际发包 trace 的字节差分计算，包含报头及重传；不同于 RNIC 内部目标速率。
- Goodput：接收侧按序有效载荷累计字节差分；不把重复包算作有效吞吐。
- Queue：接收侧瓶颈出口队列的采样值，表中峰值是 100 µs 采样峰值，不保证捕获事件级最高值。
- FCT：原始流完成时刻减开始时刻，不扣除 WAN RTT。未完成流不赋零值，也不填入中位数。
- 丢包：所有交换机累计准入丢包事件；不是去重的数据包损失率，重传可能重复遭遇丢弃。
- RTT：稀疏数据包与 ACK 匹配的辅助观测；存在重传对应歧义，不作为本报告主要定量结论。
- 收敛：每流 goodput 以 1 ms 分箱，全部活跃流落入报头修正后公平目标 ±10%，持续 7 ms。所有算法当前均未满足该标准，不能按 FCT 推断收敛速度。

三个场景共 18 次运行的退出码均为 0。同一场景六算法拓扑和流量文件哈希一致。basic 六算法的 goodput 积分均为 40 MB；incast 已完成的四种算法均为 160 MB，与计划载荷一致。

旧批次 `results/unified-cc/comparison` 存在完成流接收状态重建引起的差分下溢，已标记无效。本报告仅使用修复后 `comparison-v2` 和对应消融 `reactive-v2`。

## 六、实验结果与分析

### 6.1 基础拥塞：2→1

| 算法 | 队列峰值 MB | FCT 中位数 ms | 准入丢包事件 | 完成流数 |
|---|---:|---:|---:|---:|
| DCQCN | 14.529 | 16.816 | 15,238 | 2/2 |
| HPCC | 28.311 | 26.043 | 40,209 | 2/2 |
| TIMELY | 28.311 | 22.745 | 129,172 | 2/2 |
| Bifrost | 14.091 | 16.816 | 15,238 | 2/2 |
| FRP | 9.034 | 11.296 | 0 | 2/2 |
| Proposed | 7.278 | 15.275 | 0 | 2/2 |

Proposed 相比 DCQCN 队列峰值降低约 49.9%，FCT 中位数降低约 9.2%。在该场景中，proposed 队列峰值最低，但 FRP 的 FCT 更短，表明队列长度与完成时间之间仍存在取舍。

所有算法均发送相同有限载荷并完成，若把完成后的空闲时间也包含在相同统计窗口内，平均 goodput 都约 6.81 Gbps。这个平均值主要由总载荷和窗口长度决定，不适合据此评价吞吐控制优劣。

### 6.2 突发 incast：8→1

| 算法 | 队列峰值 MB | FCT 中位数 ms | 准入丢包事件 | 完成流数 |
|---|---:|---:|---:|---:|
| DCQCN | 21.380 | 66.455 | 462,157 | 8/8 |
| HPCC | 28.311 | — | 3,434,779 | 0/8 |
| TIMELY | 28.311 | — | 5,734,092 | 0/8 |
| Bifrost | 15.496 | 66.455 | 462,406 | 8/8 |
| FRP | 15.459 | 36.727 | 0 | 8/8 |
| Proposed | 21.749 | 43.577 | 22,126 | 8/8 |

“—”表示 80 ms 仿真结束时没有完整流可计算 FCT，不表示 FCT 为零。

相对 DCQCN，proposed 的 FCT 中位数降低约 34.4%，准入丢包事件减少约 95.2%，但队列峰值增加约 1.7%。这说明 proposed 改善了流完成时间和丢包情况，但尚未抑制 incast 的初始队列峰值。

FRP 在该场景的队列、FCT、准入丢包指标均优于 proposed。Bifrost 降低了接收侧队列，但 FCT 与 DCQCN 相同，其原因还需要结合源侧积压和重传情况分析。

HPCC、TIMELY 尚未完成；goodput 积分分别为 33.568 MB、39.594 MB，低于计划的 160 MB。由于这两种算法的参数和运行行为仍需核查，本文暂不以它们作为评价 proposed 改善幅度的主要依据。

### 6.3 动态增减流：2→8→2

| 算法 | 全程队列峰值 MB | 20–45 ms 平均 goodput Gbps | 70–80 ms 平均 goodput Gbps | 准入丢包事件 |
|---|---:|---:|---:|---:|
| DCQCN | 28.311 | 18.359 | 25.934 | 565,298 |
| HPCC | 28.311 | 0.015 | 0.080 | 1,975,025 |
| TIMELY | 28.311 | 0.001 | 1.364 | 4,250,976 |

Proposed 在增流窗口的 goodput 高于 DCQCN，且全程丢弃更少。但减流后末段 goodput 低于 DCQCN 和 FRP，有效载荷速率仅相当于 50 Gbps 链路速率的 35.6%。虽然这一比例未扣除报头开销，仍可看出明显的带宽利用不足。

Proposed 在 70–80 ms 的 goodput 变异系数约为 0.034，DCQCN 约为 0.813。proposed 的吞吐波动较小，但平均值偏低，说明它稳定在了较低的发送水平。

![Proposed 动态实验](../results/unified-cc/comparison-v2/dynamic/proposed/overview.png)

减流后恢复缓慢可能与 CNP 执行方式有关：降速由近源通知触发，而提速依赖 DCQCN 自身的恢复机制。另一种可能是旧反馈仍在影响发送端。需要对齐目标速率、CNP、实际 TX 和队列的时间序列，判断限制主要出现在控制器还是 RNIC。

### 6.4 预测机制消融

对照版保留接收侧真实队列控制、近源虚拟队列、CNP 和保护机制，仅关闭预测队列项，即 `--proposed-control 1`；预测版为 `--proposed-control 2`。

| 指标 | 关闭预测 | 开启预测 |
|---|---:|---:|
| basic 队列峰值 MB | 7.278 | 7.278 |
| basic FCT 中位数 ms | 15.234 | 15.275 |
| incast 队列峰值 MB | 21.749 | 21.749 |
| incast FCT 中位数 ms | 43.542 | 43.577 |
| incast 准入丢包事件 | 22,126 | 22,126 |
| dynamic 队列峰值 MB | 21.673 | 21.880 |
| dynamic 20–45 ms goodput Gbps | 30.599 | 31.591 |
| dynamic 70–80 ms goodput Gbps | 17.843 | 17.782 |

预测在 basic/incast 中没有带来可见优势；dynamic 增流窗口 goodput 约高 3.2%，但队列峰值也略高，减流恢复没有改善。目前每种配置仅运行一次，这一差异是否具有代表性还需重复实验确认。

关闭预测后，相对 DCQCN 的主要改善仍然存在。因此，现阶段的收益更可能来自接收侧队列控制与近源 CNP 的共同作用。现有消融还不足以区分这两部分各自的贡献，也没有说明预测项能带来稳定的额外收益。

## 七、当前结论

### 7.1 初步结论

1. 在既有 workload 框架内，六算法可以使用统一入口完成三类小规模实验；程序正常退出不代表所有流均完成。
2. Proposed 已实现“接收侧控制—延迟目标反馈—近源虚拟队列—真实 CNP—RNIC 调速”闭环。
3. 相比当前 DCQCN，proposed 在 basic 中降低队列，在 incast 中改善 FCT 和准入丢包；改善依赖具体场景。
4. Proposed 没有降低 incast 队列峰值，尚未优于当前 FRP 对照；减流后的吞吐恢复不足。
5. 当前零阶预测没有显示稳定的独立优势。按现有严格收敛判据，所有算法都未达到持续公平目标，暂不能报告“收敛更快”。

### 7.2 尚待验证的问题

- 长反馈时延、RNIC 执行滞后及在途流量共同造成初始队列峰值。
- 近源 CNP 缩短局部降速反馈路径，可能减少后续过量发送和丢弃。
- 旧反馈、活跃流识别误差或 DCQCN 自身恢复机制，可能导致减流后长期低速。
- 固定速率外推无法准确表达指令逐步生效的过程，可能解释预测收益有限。

上述分析仍需通过控制时序和消融实验验证。本轮实验规模较小，基线参数也尚未充分适配，结论主要适用于当前配置。

## 八、下一步工作

接下来先分析现有日志，明确预测收益有限和减流恢复缓慢的原因，再据此修改控制逻辑。FRP 保留为对照，本阶段不继续优化。

| 优先级 | 要做什么 | 主要观察什么 | 完成标准 |
|---|---|---|---|
| P0 | 对齐 proposed 动态实验控制日志与逐流速率 | 45 ms 后 target、source_target、虚拟队列、CNP 增量、实际 TX、goodput；区分停止注入与在途排空 | 判断低吞吐主要发生在目标计算、近源执行还是 RNIC 恢复环节 |
| P0 | 核查 incast 初始峰值来源 | 首批数据、首次遥测、首次目标到达、首次 CNP、实际降速、接收侧峰值的时刻 | 形成一张时间线，明确控制最早能影响哪一段队列增长 |
| P0 | 核查预测是否真正改变动作 | q̂−q、预测误差、上下限命中、两版本目标差异、CNP 差异 | 判断预测无收益是预测错误、被限幅掩盖还是执行器没有跟随 |
| P0 | 复核 HPCC/TIMELY baseline | RTT 阈值、窗口配置、INT、PFC 和重传；先做无拥塞单流验证 | 基础传输正常，再决定是否进行单项参数适配；保留旧结果与配置 |
| P1 | 估计实际执行延迟 d₀ | 指令发出、源侧登记、实际出口变化及接收变化 | 给出可重复的延迟测量，替代仅靠固定 H 的假设 |
| P1 | 加入预测误差校准的小消融 | 无预测 / 固定预测 / 校准预测，同一流量下比较 | 预测误差下降，同时 FCT、队列或恢复有收益，且没有明显副作用 |
| P1 | 根据 P0 结论修正减流恢复 | 目标已升高时是否仍发 CNP、活跃流误判、RNIC 恢复斜率 | 在不恶化 incast 丢包和峰值的前提下，提高末段有效吞吐 |
| P1 | 补少量重复与公平性统计 | 多个种子或轻微到达扰动、逐流 goodput、Jain 指数 | 关键结论不依赖单次时序，避免只看聚合值 |
| P2 | 网络化跨域反馈、多流组、复杂拓扑和大 workload | 控制报文开销、丢失、乱序与状态规模 | 核心机制验证后再开展 |

近期先完成控制时序分析，定位减流后低吞吐的原因，并补充区分预测与近源 CNP 作用的消融实验。大规模参数搜索暂不开展。
