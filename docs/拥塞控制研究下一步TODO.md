# 拥塞控制研究：下一步 TODO

依据：[第一版实验报告](初步实验报告-20260917.md)、[v0.5 实验草案](拥塞控制方案v0.5-实验草案.md)。

目标：先解释已有结果，再完善执行器和预测器，最终判断新机制是否有独立收益。以下都是待办，不表示已经实现或验证。

## 先记住当前结论

- 近源虚拟队列/CNP 已在当前实验中改善队列、有效吞吐和有限流完成情况。
- 流加入场景中，开启和关闭预测的性能相同；目前不能把收益归因于预测。
- 新方案仍有吞吐空洞，没有达到持续公平满速的收敛要求。
- 当前结果是小拓扑、单种子结果；大拓扑、预测精度和执行时延仍待验证。

**接下来先做 P0-1～P0-3：复查结果 → 补齐控制链路观测 → 单独验证执行器。不要一开始就调整预测公式或扩大实验规模。**

## P0：必须先完成

### P0-1：复查现有结果，列出真正要解释的问题

**为什么做：** 先确定差异发生在哪一层，避免针对错误原因改算法。

- [ ] 打开 [join 总览图](../results/research-20260917/pilot/figures/join-overview.png)，标出新流加入、队列上升、首次丢包、发送下降、吞吐恢复的时间。
- [ ] 对比 reactive-cnp 和 predictive-cnp 的目标、CNP、发送、队列轨迹，不只比较最终均值。
- [ ] 列出吞吐空洞的时间区间，检查该区间流是否仍有数据可发；有限流完成后的空闲不算退化。
- [ ] 写下三个待解释问题：为什么预测目标不同但效果相同？为什么近源版本仍间歇停发？哪些收益可能只是来自预配置的100Gbps组容量？

**主要观察：** 接收队列、源侧真实TX、跨域出口TX、接收goodput、目标速率、CNP与PFC时间。

**完成标准：** 给出一张带事件标注的时间轴；区分“已从数据看到”和“需要新增观测才能判断”。

**下一步：** 只为这些问题补观测字段。

### P0-2：补齐“目标 → CNP → 实际速率”的控制链路日志

**为什么做：** 控制目标改变不等于RNIC已经执行，累计CNP数量相同也不等于发送时刻与对象相同。

- [ ] 给每次远端目标加编号，记录生成时刻、发送侧登记时刻、目标组、目标速率、用于计算的状态时间戳。
- [ ] 在发送DCI记录虚拟队列z、周期进入字节Din、登记目标u、活跃流数、每流实测速率。
- [ ] 记录每次CNP的对象、发送/接收时间，以及未发送的原因：z未过阈值、流未超过份额、流已不活跃等。
- [ ] 区分近源CNP与原端到端ACK上的ECN触发，记录RNIC控制速率及实际发送速率。
- [ ] 对吞吐空洞补记：是否有待发字节、窗口是否受限、在途字节、PFC暂停状态、下一次可发送时间。
- [ ] 把新增日志画到同一时间轴；快速执行过程优先用事件日志或100µs采样，不用1ms采样推断微秒级响应。

**主要观察：** 目标是否按时登记？z是否变化？门控是否变化？CNP是否真正到达？RNIC控制速率与实际TX是否同时变化？

**完成标准：** 至少追踪一次目标下降和一次恢复全过程；能将一次吞吐空洞定位到具体状态，而不是笼统称为“收敛慢”。

**代码入口：** [longhaul-research.h](../simulator/ns-3.39/examples/PowerTCP/longhaul-research.h)、[rdma-hw.cc](../simulator/ns-3.39/src/point-to-point/model/rdma-hw.cc)。

### P0-3：单独验证近源执行器能否跟踪目标

**为什么做：** 如果执行器无法区分两个目标，改进上层预测也未必改变发送行为。

- [ ] 新建一个诊断实验，固定流量和拓扑，向近源模块输入一组预设目标阶跃，例如100 → 70 → 100Gbps；每段至少覆盖若干基础RTT。
- [ ] 为隔离执行器，诊断时关闭远端目标计算；不要把预设目标阶跃包装成真实控制算法结果。
- [ ] 同时观察下调响应和上调恢复：首次明显变化需要多久、达到目标范围需要多久、是否长期低于目标。
- [ ] 区分近源CNP与原ECN的作用；如果它们难以区分，再做一次仅用于诊断的对照。正式算法比较仍保留一致的ECN/PFC配置。
- [ ] 检查门控死区、虚拟积压、活跃流超时和DCQCN恢复机制；发现哪一项限制跟踪，就只改那一项，并保留修改前后对照。

**主要观察：** 目标跟踪误差、CNP对象与频率、实际TX过冲、恢复耗时、z是否长期积压。

**完成标准：** 能回答“执行器可以控制什么范围、响应多快、什么情况下失效”。如果上调目标后仍无法恢复，应先解决或明确这一限制，再做预测。

### P0-4：辨识实际生效时延，替换拍定的H

**为什么做：** 当前H=10.033ms只是名义值，没有完整包含CNP周期、排队、网卡响应和源队列的影响。

- [ ] 定义并记录：t0=接收侧发出目标；t1=源DCI登记；t2=源DCI实际出口速率出现持续响应；t3=接收侧到达速率出现对应响应。
- [ ] 分别计算目标返回延迟t1−t0、源侧执行响应t2−t1、前向响应传播t3−t2和总生效时间t3−t0。
- [ ] 在单次阶跃诊断中预先定义“持续响应”的幅度阈值与保持时间，避免看完曲线后移动判定标准。
- [ ] 无明确响应时记录“未响应/无法识别”，不能记成0；重叠目标下不能强行给每个速率变化归因。
- [ ] 明确预测时间范围是否还包含控制采样等待T；写清H与L的关系，避免漏算或重复加周期。

**主要观察：** 下调与恢复的时延是否不同？拥塞/PFC时是否变长？源DCI出口变化是否晚于RNIC速率变化？

**完成标准：** 给出至少一组可核验的响应时间线，并说明固定H是否足够；不确定时先使用明确标注的保守范围。

### P0-5：验证预测精度，再决定如何改预测器

**为什么做：** 必须先证明模型对未来状态有用，不能只证明公式可以计算。

- [ ] 保存每次预测的生成时间、目标时间t+H、q_hat、已知发送统计及其采样区间。
- [ ] 把q_hat(t+H)与实际q(t+H)对齐比较；不能与q(t)比较后宣称预测准确。
- [ ] 至少报告平均绝对误差、危险的低估误差、保守的高估误差；将突发、恢复、稳定阶段分开看。
- [ ] 与“未来队列保持当前q不变”的简单预测对照；固定日志上的离线预测比较只能证明预测误差，不能证明闭环性能提升。
- [ ] 如果零阶外推失败，先判断是H错误、源端执行未完成、源队列/PFC改变到达，还是接收侧服务能力改变。
- [ ] 按诊断结果只加最必要的一项状态，例如实际执行响应或尚未生效的目标；暂不同时加入复杂残差学习和大量参数。

**主要观察：** 是否重复把旧高发送速率外推到整个H？目标尚未执行却被当成已生效了吗？真实队列重置后又加E，是否重复纠偏？

**完成标准：** 得到一张预测误差图和原因说明。预测不优于简单对照时，保留负面结论，暂不宣称预测有效。

### P0-6：用最小消融明确收益来源

**为什么做：** 当前初始容量约束、近源执行、接收反馈和预测同时存在，需要拆开贡献。

- [ ] 在同一个join场景比较下表四个版本；“固定目标近源版”需要新增，不是当前runner已有选项。
- [ ] 先比较每组目标、CNP事件和实际TX是否不同，再比较性能指标。
- [ ] 当两个版本输出一致时，定位原因并停止重复跑同类实验；不要仅凭组合版本优于baseline宣称每个模块都有效。

| 版本 | 用途 |
|---|---|
| 原DCQCN | 判断增加近源机制的总体作用 |
| 固定容量目标 + 近源VQ/CNP | 判断预配置容量约束本身的作用 |
| 接收实测队列控制 + 同一近源执行器 | 判断远端自适应反馈的作用 |
| 接收预测控制 + 同一近源执行器 | 判断预测的额外作用 |

**主要观察：** 队列峰值/面积、goodput、CNP事件、吞吐空洞、恢复时间，以及同一条件下的FCT和公平性。

**完成标准：** 每个新增机制都有对应消融；结论明确写成“哪个机制带来了哪项变化”，包括没有收益或存在副作用。

## P1：P0完成后，再增强实验说服力

### P1-1：增加一个真正需要远端状态的场景

- [ ] 保持现有小拓扑，让远端长流先稳定，再让接收DC本地背景流加入并退出，竞争同一接收出口。
- [ ] 远端受控组和本地背景流分别统计；近源CNP只控制远端组，不能误控本地流。
- [ ] 修改当前“所有流必须来自发送DCI直连主机”的研究限制，并同步修改分析脚本的固定流数/源ID假设；不要直接把本地流塞进现有流文件运行。
- [ ] 若控制器需要估计远端可用容量，明确它如何由可观测状态得出；低离开速率可能只是队列空，不能直接当作服务能力下降。
- [ ] 先比较固定目标、反应式、预测式三个版本；只有机制开始表现出差异，才补齐HPCC/TIMELY比较。

**主要观察：** 本地流加入后的远端降速、队列积累；本地流退出后的带宽回收、恢复时间和长期低利用率。用组内公平份额评价远端流，不沿用固定100Gbps/N目标。

**完成标准：** 说明这个场景为何需要接收侧信息，以及预测是否在同一执行器上进一步改善；不要求一定得到正面结果。

### P1-2：补充鲁棒性和完整性能指标

- [ ] 只对一个最有解释力的场景增加少量独立RngRun，先做3次，逐次展示结果与范围；样本少时不夸大统计显著性。
- [ ] 检查随机流是否真的随RngRun变化；完全确定的实验重复得到相同结果，不能替代场景鲁棒性验证。
- [ ] 有限流报告完成数/总数；必要时统一延长所有版本仿真时间，仍未完成则保留右删失，不把缺失FCT算零。
- [ ] 补实际RTT观测，标明从哪个发送事件量到哪个ACK接收事件；对重传歧义明确处理。基础RTT和q/C只能作为参照，不能冒充实测RTT。
- [ ] 区分独特有效字节、实际线速字节、重传、准入丢包、ECN与PFC；全局准入丢包计数不等于独特丢包数。
- [ ] 收敛沿用预先定义的公平目标范围与保持时间；未满足仍报未收敛，不能用队列下降时间替代满速收敛。

**完成标准：** 能描述收益是否稳定、是否牺牲吞吐/公平性/恢复/FCT，而不仅是展示一张更低的队列图。

### P1-3：更新方案和报告

- [ ] 用一段话写清“问题 → 原因 → 新增机制 → 可观测控制信号 → 执行方式 → 实验效果”。
- [ ] 明确远端控制组如何映射到接收出口，谁知道组容量，谁发现活跃流，成员退出后何时移除。
- [ ] 明确控制上限/下限、更新周期、超时，以及与原ECN/PFC/DCQCN恢复机制的关系。
- [ ] 将协议模拟假设列出：跨域反馈目前是延迟事件，近源CNP才是真实报文；不能据此声称已验证反馈包开销或丢失鲁棒性。
- [ ] 分开写已验证、原因推测、尚未验证；只有预测消融支持时，才把预测写成已验证贡献。

**完成标准：** 读者不看代码也能理解系统闭环，且每条性能结论都能对应到一组公平对照。

## P2：机制明确后再做

- [ ] 回到原64主机/DC大拓扑，核验路由、瓶颈位置、组映射及ECMP影响。
- [ ] 修复并单独验证超大流分包截断和32位序号回绕；当前≤2GB只是规避，不是修复。
- [ ] 实现真实跨域反馈报文，测试反馈丢失、乱序、过期信息与开销。
- [ ] 扩展多组、多瓶颈、不同RTT公平性和更复杂负载。
- [ ] 在机制和证据明确后再做较大参数搜索、稳定性分析或架构重构。

## 每次实验都要检查

- [ ] 一次只回答一个问题，运行前写下预期现象及能推翻假设的结果。
- [ ] 使用新的输出目录，保存源码版本/差异、有效配置、输入、种子、命令、退出码和原始CSV。
- [ ] 对比双方使用相同拓扑、流量、buffer、ECN/PFC、窗口、采样和仿真时间；必要差异明确列出。
- [ ] 时延变化时检查发送窗口、headroom等派生参数，不能误称“只改变反馈延迟”。
- [ ] 继续核验队列字节守恒与信息时间戳；不用程序即时全局状态给控制器提供远端信息。
- [ ] 同时看队列和goodput；队列低但链路空闲不算成功。Jain高但所有流都很慢也不算成功。
- [ ] 一个实验已经解释问题就停止扩展；不支持假设时记录失败原因，决定修实现、改假设还是换场景。
