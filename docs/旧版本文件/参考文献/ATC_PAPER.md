# 重新架构跨数据中心 RDMA 网络中的流量控制

> **原文标题**：Re-Architecting Traffic Control in Cross-Datacenter RDMA Networks  
> **作者**：Zirui Wan, Jiao Zhang, Yuzhen Su, Haoyu Pan, Mingxuan Yu, Yuan Li, Tao Huang  
> **发表**：IEEE Transactions on Networking, 2025, DOI: 10.1109/TON.2025.3569630

---

## 摘要

网络密集型应用（如机器学习和云存储）正推动两大趋势：1）RDMA 被大规模部署以提供高速网络；2）应用分布式地部署在多个区域数据中心以满足内容提供商和客户的需求。为充分发挥 RDMA 的优势，我们希望将其扩展到跨数据中心网络。然而，长距传输的控制环路显著变长，长距流与数据中心内部流混合容易引发严重拥塞。本文提出 **Approach Traffic Control（ATC）**，一种聚焦于两侧 DCI 交换机（即数据中心的"进近点"）的新型方案，分别缓解本地和远端数据中心的混合流量拥塞，并作为现有主机驱动拥塞控制方法的构建块。该设计原则使 ATC 将控制环路缩短到单个数据中心尺度，同时以较低的部署复杂度聚合整个数据中心范围的拥塞信息。我们在 P4 可编程交换机上实现 ATC，并通过真实测试床和大规模 NS3 仿真进行评估。结果表明，ATC 能够快速避免拥塞并显著提升性能：数据中心内部流和长距流的 FCT 分别降低最多 88% 和 52%。

**关键词**：RDMA 网络、跨数据中心网络、拥塞控制

# I. 引言

远程直接内存访问（RDMA）以近零 CPU 开销实现高吞吐和低延迟。凭借这些优势，RDMA 正成为一种流行的高速网络技术，已被现代数据中心广泛部署。例如，Microsoft Azure 中约 70% 的流量是 RDMA。另一个趋势是，地理分布式机器学习和云存储等应用被分布式部署在多个区域数据中心，以满足客户和内容提供商的需求（如 Azure、Google、Facebook、Amazon 和 Alibaba）。

为充分发挥 RDMA 的优势，我们希望将其扩展到跨数据中心网络。原因有三：第一，与广域网（WAN）不同，区域数据中心通过专用长距光纤和 DCI 交换机连接，这使运营商能够建立和管理跨数据中心网络上的 RDMA 传输。第二，RDMA 可以实现每连接 100Gbps 的吞吐量和近零 CPU 开销，而 TCP 协议栈在长距传输中尤其存在单核吞吐量低和持续高 CPU 消耗的问题。第三，运营商不愿同时管理两种网络，维持 RDMA 在跨数据中心网络中的使用可以避免这一问题。

然而，设计长距 RDMA 流量控制方法面临挑战。由于跨数据中心网络的 base-RTT 显著大于单数据中心尺度，长距传输的控制环路大幅延长。结果是，长距流与数据中心内部流的混合使网络状态复杂化，容易引发严重拥塞（即混合流量拥塞）。同时，数据中心内部交换机的浅缓存相对于长距传输的大带宽延迟积（BDP）而言十分有限，容易触发缓存溢出并导致 PFC 暂停。

此外，我们发现现有 RDMA 流量控制方法主要适用于数据中心内部网络，无法应对上述挑战。一方面，主机驱动方法（如 DCQCN、TIMELY、HPCC）控制环路长，无法及时检测拥塞。另一方面，交换机驱动方法难以平衡部署难度与拥塞控制范围之间的关系。

本文提出 **Approach Traffic Control（ATC）**，一种聚焦于两侧 DCI 交换机的新型解决方案，分别缓解本地和远端数据中心的混合流量拥塞，作为所有现有主机驱动控制方法的构建块。DCI 交换机驱动方案的设计原则使 ATC 将控制环路缩短到单数据中心尺度，同时以较低的部署复杂度聚合整个数据中心范围的拥塞信息（例如，ATC 与 RNIC 硬件级 DCQCN 兼容）。

ATC 是一个易于部署的构建块。我们在 P4 可编程交换机上实现 ATC 的 DCI 交换机流水线，并将其与主机驱动控制方法集成。我们进一步构建真实测试床和大规模 NS3 仿真来评估 ATC 的性能。大量结果表明，ATC 确保了快速拥塞避免并带来了显著的性能提升。例如，ATC 将数据中心内部和跨数据中心流量的 FCT 分别降低最多 88% 和 52%。

**主要贡献：**

- 我们提出了支持长距 RDMA 传输的需求，并研究了现有流量控制方法的局限性：(i) 主机驱动方法控制环路长；(ii) 交换机驱动方法难以平衡部署难度与拥塞控制范围。
- 我们提出 ATC，一种新型长距 RDMA 流量控制解决方案，聚焦于两侧 DCI 交换机以分别缓解本地和远端数据中心的混合流量拥塞，作为所有主机驱动方法的构建块。
- 我们在商用 P4 可编程交换机上实现 ATC，并通过真实测试床实验和 NS3 仿真进行评估。大量评估结果表明，ATC 是增强跨数据中心 RDMA 网络性能的有前景的基座。

需要注意的是，尽管 ATC 是为 RDMA 网络设计的，我们相信其洞察和设计也适用于其他高速跨数据中心网络。

# II. 背景

本节首先介绍跨数据中心应用的广泛部署，然后阐述提供长距 RDMA 支持的必要性。

## A. 跨数据中心应用部署

**多数据中心部署。** 近年来，高性能应用被分布式部署在多个数据中心，原因有二：第一，单个数据中心在计算和存储方面存在容量限制，因此大规模数据密集型应用被扩展到多个数据中心以获取足够资源。第二，分布式应用满足客户需求，包括最小化访问延迟（如 CDN）、使用本地数据遵守数据驻留法规、支持定期数据备份以及提供更好的灾难恢复能力。

**跨数据中心流量特征。** 一般而言，跨数据中心流量可分为两类。第一类称为前端用户生成流量，源自用户的即时需求（如视频服务、在线聊天）。第二类称为后端业务流量，源自数据处理或迁移（如地理分布式机器学习系统、Web 搜索系统）。近年来，后端流量显著增长，对数据中心间连接性能提出了新挑战。

**数据中心互联（DCI）系统。** 大型数据中心运营商利用专用长距光纤连接其数据中心（如 Google B4、Microsoft Global WAN、Facebook Backbone）。为满足区域服务等级协议（SLA）和光纤限制，DCI 系统要求数据中心间专用光纤长度约 120 km，往返延迟约 1 ms。数据中心间连接有多种选择，图 1 展示了常见方案。每个数据中心有一个外部 DCI 交换机连接其核心交换机，然后 DCI 交换机通过彩色光收发器和光纤连接对端。这些基础设施支持密集波分复用（DWDM）以最大化光纤利用率并增加带宽。

> **图 1.** 数据中心互联系统。

## B. 为什么需要长距 RDMA？

**数据中心内的 RDMA。** RDMA 是一种创新的高速网络技术，具有内核旁路和传输卸载能力。RDMA 可以以低 CPU 开销实现高吞吐和低延迟。由于这些优势，部署 RDMA 以增强底层网络已成为趋势。由于 InfiniBand 的高成本和封闭架构，另一种 RDMA 技术——RoCEv2（RDMA over Converged Ethernet Version 2）正成为现代高速数据中心的事实标准。

**长距 RoCEv2。** 为充分发挥 RDMA 的优势，我们希望将其扩展到跨数据中心网络。原因有二：

一方面，跨数据中心应用（如在线流媒体和数据备份）需要高吞吐来传输大型数据集。我们在两个通过专用 100Gbps 链路连接的数据中心之间进行了简单的测试床实验。如图 2 所示，RDMA 提供约 100Gbps 的单连接吞吐量和近零 CPU 开销，而传统 TCP 的带宽仅为几十 Gbps，且 CPU 开销高得难以接受，尤其在跨数据中心传输中。

> **图 2.** 不同流数量下 TCP 和 RDMA 传输在数据中心内部和跨数据中心场景中的吞吐量与 CPU 核利用率。RDMA 在两种场景中均能以低 CPU 开销实现高吞吐。

另一方面，运营商不愿同时管理两种网络。例如，在 RDMA/TCP 混合部署过程中，高 I/O 密集型 TCP 会大量消耗 PCIe 带宽并引发大量 TX 暂停（即 NIC 发送的 PFC 暂停），可能导致 PFC 风暴。维持 RDMA 在跨数据中心网络中的使用可以避免数据中心运营商和应用开发者管理两种网络（或编程接口）。

# III. 动机

本节首先分析跨数据中心 RDMA 网络中速率控制的需求和挑战，然后提出新长距 RDMA 流量控制方法的设计目标。

## A. 现有速率控制方法不足

**无损 RDMA。** 为实现高效运行，RoCEv2 依赖 PFC 维持无损网络（即不因交换机缓存溢出而丢包）。当入队长度超过阈值时，交换机向上游发送 PAUSE 消息，上游停止发送直到收到 RESUME 消息。PFC 会带来队头阻塞（HoL）、PFC 风暴甚至死锁等问题。解决这些问题的根本方法是基于流的速率控制。

> **图 3.** 现有控制方法概览。

> **图 4.** 混合流量拥塞概览。

然而，与数据中心内部通信不同，长距传输面临三个主要挑战：(i) base-RTT 和 BDP 显著大于单数据中心尺度，因此长距流的控制环路更长；(ii) 数据中心内部流与长距流混合使网络状态复杂化，容易引发严重拥塞（即混合流量拥塞），如图 4 所示——当长距流突发（Case-3）或与本地（Case-1）/远端（Case-2）数据中心内部突发流冲突时就会发生拥塞；(iii) 数据中心内部盒式交换机的缓存较浅，相对于长距传输的大 BDP 而言很容易触发缓存溢出并引发 PFC 暂停。我们发现现有速率控制方法不足以应对这些挑战（如图 3 所示），可大致分为两类：(i) 主机驱动方法和 (ii) 交换机驱动方法。

**主机驱动速率控制的问题。** 主机驱动方法沿端到端环路收集拥塞信号（如 DCQCN 中的 ECN、TIMELY 中的网络延迟、HPCC 中的 INT）。长距传输显著增加了反馈延迟，使发送方无法及时检测拥塞。结果是长距流会收敛到错误点。

我们进行了 Case-1 和 Case-2 的混合实验：分析默认部署的 RNIC 算法 DCQCN 和最先进的 HPCC。我们进行 NS3 实验，设置与评估设置相同。一条长寿命背景流在时刻 0 从 DC-A 发送到 DC-B 中的一个接收者。然后，七条本地数据中心内部突发流在时刻 0.8ms 从与背景流相同的 Pod 发出，另外七条远端数据中心内部突发流在时刻 4.8ms 发送到与背景流相同 Pod 内的接收者。

> **图 5.** 数据中心内部突发流在 0.8ms 和 4.8ms 启动。长距流与数据中心内部突发流冲突时的吞吐量和交换机队列长度。端口 1 和端口 2 是 DC A 和 B 中的两个拥塞端口。ATC 可以快速降低队列长度并缓解性能下降。

图 5 显示了吞吐量和交换机队列长度。可以看到，由于长反馈延迟，队列长度峰值达到 6MB，触发 PFC 并持续降低数据中心内部和长距流量的发送速率。结果是网络收敛到错误状态。在最坏情况下，长距流吞吐量降为 0 并等待很长的增长间隔才能恢复。

> **图 6.** 不同 host-driven 方法配置下各类流量的吞吐量。增大发送窗口略微提升吞吐量，而单独优化配置会导致公平性问题。

然后，我们改变配置，使用增大发送窗口的 DCQCN 或不同窗口配置的 HPCC（数据中心内部优化或单独优化）进行实验。图 6 显示了结果。可以看到，增大发送窗口略微提升吞吐量。另一方面，尽管单独优化窗口的 HPCC 性能更好，但它在长距流和突发流之间存在不公平性。这是因为两种流量的 RTT 和初始发送窗口不同，加性增长因子 WAI 在长距场景中失效。结果是突发流遭受长尾 FCT。此外，数据中心内部优化配置对长距流性能造成严重惩罚。这些结果表明，长反馈延迟是主机驱动速率控制性能下降的根本原因，无论速率调整如何实现。

我们还评估了 GEMINI 的性能。图 7 显示了吞吐量和交换机队列长度。由于 GEMINI 的长端到端控制环路和基于延迟的拥塞信号对长距流的低效性，吞吐量收敛仍然缓慢，队列长度峰值达到 12MB 并触发 PFC。

> **图 7.** 数据中心内部突发流在 0.8ms 和 4.8ms 启动。GEMINI 的吞吐量和队列长度。长端到端控制环路和基于延迟的信号对长距流的低效性仍使 GEMINI 无法及时缓解拥塞。

**交换机驱动速率控制的困境。** 交换机驱动方法需要平衡部署难度与拥塞控制范围。我们按关键交换机位置将其分为：(i) 近源交换机反馈方案；(ii) 逐跳交换机控制；(iii) 代理交换机控制。我们重复之前的实验，使用交换机驱动速率控制方法并展示结果如图 8 所示。

> **图 8.** 不同 switch-driven 速率控制下各类流量的吞吐量。Annulus 仅部署在 ToR 上但性能较差。RoCC 和 BFC 性能更好但需要在所有交换机上部署。Azure 和 SWING 仍维持长控制环路，在处理混合数据中心内部拥塞时与纯 DCQCN 结果类似。相比之下，ATC 确保高性能且易于部署。

**近源交换机反馈方案**直接从交换机向发送方发送反馈（如 Annulus、RoCC）。Annulus 仅在 ToR 上部署 QCN 标准来解决 ToR 内部突发拥塞，因此无法解决多 ToR 突发，且长距流在远端混合拥塞场景中仍维持长控制环路。图 8(a) 显示 Annulus 相比纯 DCQCN 仅有微小改善。而 RoCC 在网络中每台交换机上启用类 QCN 机制，商用数据中心部署困难。此外，图 8(b) 显示 RoCC 缺乏对拥塞的全局判断，倾向于对背景流和突发流过度反应。由于长的发送方到远端控制环路，RoCC 也无法解决远端数据中心的拥塞。

**逐跳交换机控制方案**提供逐跳逐端口流控制（如 BFC、Floodgate）。这些方案在每台交换机中维护多个队列以吸收突发包，并通过逐跳信用控制解决拥塞。然而，逐跳控制增加了部署难度。图 8(c) 显示 BFC 由于浅缓存数据中心内部交换机的背压，背景流仍存在性能下降。在高负载下，长距流拥塞会蔓延到数据中心内部交换机，对队列使用数量造成压力，增加哈希冲突并导致 HoL 问题。我们进行了实验来说明这一点：数据中心内部流量 30% 负载，跨数据中心流量 30% 负载。我们监控交换机中 VOQ 使用的最大数量，表 II 显示了结果。可以看到，#2 交换机的最大数量达到 39。相比之下，ATC 的最大数量仅为 7。

> **表 I.** 商用数据中心内部交换机和 DCI 交换机的缓存大小。

> **表 II.** BFC 在交换机中使用的最大 VOQ 数量（#2 交换机达到 39；ATC 最大仅为 7）。

**代理交换机控制方案**使用代理交换机互联数据中心（如 Bundler）。这些方案主要通过在两侧的中间盒中聚合和存储长距流来关注长距链路拥塞，然后在中间盒之间执行调度策略。代理的交换结构严重降低了长距链路吞吐量，仅几百 Mbps。类似地，SWING 利用 DCI 交换机之间的 PFC-Relay 确保长距链路吞吐量，Bifrost 预先暂停本地 DCI 交换机以减少缓存使用，Azure 利用 DCI 交换机上的片外 DRAM 存储 RDMA 包。然而，这些方案也主要关注长距链路拥塞，仍维持长控制环路，无法解决本地和远端数据中心的混合流量拥塞。因此，如图 8(d) 所示，Azure、SWING 和 Bifrost 与纯 DCQCN 表现类似。

**有损 RDMA。** 近年来，许多研究倡导有损 RDMA，通过用高效的基于位图的选择性重传（SR）替代 go-back-N 机制来消除 PFC。在长距传输场景中，SR 机制可以减少浅缓存数据中心交换机和随之而来的 PFC 暂停帧扩散造成的性能影响。然而，生产级全面的 PFC-free 解决方案仍不成熟，且大的长距 BDP 对其位图池和固定位图大小配置造成压力。本文主要关注与此类有损 RDMA 工作正交且互补的速率控制方案。我们相信有损 RDMA 的发展将改善长距传输。

## B. 经验教训与设计目标

我们为新长距 RDMA 流量控制方法提出以下设计目标：

1. **快速拥塞避免。** 新方案应缩短控制环路以及时检测拥塞。
2. **大范围拥塞控制并保证高性能。** 新方案应在整个数据中心范围内维持拥塞控制范围以应对大规模复杂拥塞。同时，新方案应与数据中心内部流量控制兼容以确保高性能。
3. **易于在商用数据中心部署。** 新方案应足够简单，以便对现有生产数据中心进行最小化增量改动，并能在商用实体（如 RNIC 和浅缓存数据中心内部交换机硬件）上可行部署。

**进近控制初步方案。** 一个直观的想法是将端到端控制环路分为三个独立控制，依靠两侧 DCI 交换机（即数据中心的进近点）分别控制本地和远端数据中心的混合流量拥塞，而将纯数据中心内部拥塞委托给主机驱动控制方法。这有三个主要好处：(i) 控制环路缩短到单数据中心尺度；(ii) DCI 交换机可以通过监控拥塞信号（如检测 ECN 标记、记录时间戳计算 RTT、跟踪 INT 信息）聚合整个数据中心范围内长距流的相对链路负载信息，与部署的主机驱动方法对齐。这些能力得到现代商用可编程交换机的支持，因此 DCI 交换机提供更大的控制范围；(iii) 该方案易于在生产数据中心部署。

**ATC 概览。** 我们用 ATC 重复之前的实验，发现 ATC 可以快速将队列长度降低最多 94%，从而确保长距流和数据中心内部突发流的一致高性能。ATC 也优于其他交换机驱动速率控制方法。

# IV. ATC 设计

本节提出 Approach Traffic Control（ATC）。ATC 的关键设计选择是依靠 DCI 交换机支持长距 RDMA 传输，同时通过与主机驱动控制方法协作维持高数据中心内部性能。如图 9 和算法 1 所示，ATC 由四个点组成：出发点（本地数据中心）、出发/到达进近点（即本地/远端 DCI 交换机）和到达点（远端数据中心）。ATC 的核心逻辑主要由三个流量控制模块组成，分别命名为出发控制、长距控制和到达控制，依次位于上述四个点之间：

> **图 9.** ATC 框架概览。

- **出发流量控制**：从本地 DCI 交换机到本地数据中心。为及时协调本地数据中心的混合流量拥塞，本地 DCI 交换机直接生成带有拥塞信息的出发反馈回发送方，显著缩短本地混合流量拥塞的控制环路。然后，发送方可以及时调整其发送速率。（§ IV-A）

- **到达流量控制**：从远端数据中心到远端 DCI 交换机。为解决远端数据中心的混合流量拥塞，ATC 在远端 DCI 交换机引入了一种新型流调度机制，基于接收方生成的到达反馈调度数据包传输。通过这种方案，ATC 可以缩短远端混合流量拥塞的控制环路并在不修改远端数据中心实体的情况下高效收敛。此外，ATC 利用虚拟输出队列（VOQ）防止 HoL 问题。（§ IV-A）

- **长距流量控制**：从远端 DCI 交换机到本地 DCI 交换机。为进一步减少 DCI 交换机中的缓存使用和 VOQ 使用数量，ATC 引入长距反馈机制，主动调度 DCI 交换机之间的包传输并满足 VOQ 不足场景。（§ IV-B）

**算法 1：Approach Traffic Control（ATC）**

```text
function DEPARTURE_TRAFFIC_CONTROL(Pkt)
    Monitor Congestion Signal(Pkt)
    Generate Departure Feedback()
end function

function LONG_HAUL_TRAFFIC_CONTROL(Pkt)
    Forward Scheduler(Pkt)
end function

end procedure
```

**ATC 的主要挑战。** 实现设计选择有三个主要挑战：(i) 控制逻辑应足够简单以在生产数据中心部署；(ii) 现有主机驱动控制有不同的反馈和速率控制方法，ATC 应与这些机制兼容；(iii) 如何高效且可扩展地分配 VOQ 资源以满足复杂的长距场景。

## A. 出发与到达流量控制

**出发控制逻辑。** 为协调本地数据中心的混合流量拥塞，本地 DCI 交换机在检测到拥塞发生（包括本地 DCI 交换机处的拥塞）时直接向发送方生成出发反馈。为确保公平性并简化部署难度，ATC 利用与部署的主机驱动方法相同的拥塞反馈。例如，使用 DCQCN 时，如果数据包被 ECN 标记，ATC 生成拥塞通知包（CNP）；使用 HPCC 时，ATC 截取 INT 头并镜像回发送方。然后，发送方收到出发反馈后，使用与部署的主机驱动方法相同的调整算法更新传输速率。

**到达控制逻辑。** 远端 DCI 交换机首先清除数据包中的拥塞标记（如 ECN 标记、INT 头），以减少其他拥塞信号的干扰并节省链路带宽。然后，远端 DCI 交换机利用以下两种机制协调远端数据中心的混合流量拥塞：

**按目的端聚合调度传输。** 为降低部署复杂度并增强可扩展性，远端 DCI 交换机通过维护按目的端聚合的调度表来限制包传输。调度表中的每个条目包含目的服务器信息和相对传输限制，因此与转发表共享相同的键和规模，但值不同。具体而言，传输限制是基于部署的主机驱动方法的速率（如转发速率）或窗口（如远端 DCI 交换机与接收方之间的 inflight 字节）。当远端 DCI 交换机收到数据包时，它检查调度表并确定该包是否可以转发。为计算传输限制，ATC 利用 ACK 作为到达反馈，因为大多数主机驱动方法在 ACK 中携带拥塞信息。然后，远端 DCI 交换机收到到达反馈后，计算远端数据中心的拥塞风险，并使用与部署的主机驱动方法相同的调整算法更新调度表，从而避免过度反应。最后，远端 DCI 交换机清除到达反馈中的拥塞标记（如 INT 头）。

**利用动态 VOQ 避免 HoL 问题。** 为避免远端 DCI 交换机处的 HoL 问题，ATC 利用动态分配的 VOQ 聚合和存储具有相同目的服务器的数据包。每个 VOQ 对应一个目的服务器。如表 I 所示，DCI 交换机采用基于 VOQ 架构的多交换机 ASIC 深缓存。VOQ 是存储发往一个出口端口的流量的一组缓存。VOQ 在出口端口有资源转发之前不会传输包。一些交换机芯片如 Jericho 和 Silicon One 可以支持 100K 个 VOQ 队列，足以满足常见生产数据中心的需求。

在 ATC 中，当远端 DCI 交换机收到数据包时，它检查该目的地是否已分配 VOQ。如果是，则表明远端数据中心已发生混合流量拥塞，数据包将被推入对应 VOQ。否则，远端 DCI 交换机检查调度表是否可以转发该包。如果不能，远端 DCI 交换机将基于 VOQ 位图为该数据包分配一个空闲 VOQ。否则，远端 DCI 交换机直接转发。

**与基于窗口的主机驱动调整兼容。** 当部署的主机驱动方法是基于窗口的方案（如 HPCC）时，ATC 利用以下两种机制与之协作：

第一，ATC 中的发送方选择限制发送方与本地 DCI 交换机之间的 inflight 字节。受益于此，发送方无需区分长距和数据中心内部流量，可以直接将初始窗口设为数据中心内部 BDP。在本地 DCI 交换机处，当数据包被转发时，出发反馈会携带相应数据包大小生成。然后，发送方收到出发反馈后，使用与部署的主机驱动方法相同的调整算法更新传输窗口并控制 inflight 字节。

第二，远端 DCI 交换机限制远端 DCI 交换机与接收方之间的 inflight 字节，并将初始窗口大小设为数据中心内部 BDP。接收方将收到的数据包大小插入对应的到达反馈。然后，远端 DCI 交换机收到到达反馈后，计算 inflight 字节并更新传输限制。

**与远端数据中心负载均衡机制兼容。** ATC 在远端 DCI 交换机以按目的端聚合的方式调度流量。然而，在等价多路径（ECMP）负载均衡机制下，不同 5-tuple 的流量可能通过远端数据中心的不同链路并获得错误的拥塞信息。为解决此问题同时确保数据中心内部流量继续受益于基于 ECMP 的负载均衡，有两种机制：(i) 特定 ECMP 模块——一些商用交换机有基于目的端的 ECMP 路由模块，确保按目的端聚合的流量走相同路径；(ii) ECMP 欺骗——远端 DCI 交换机向数据包插入伪造头，使基于 ECMP 的路由对相同目的端的流量产生相同结果。当生产数据中心支持时，ATC 选择第一种机制；否则使用第二种。此外，由于 ACK 具有最高优先级且数据中心通常使用对称结构的 FatTree 拓扑，来自同一接收方的 ACK 确保在远端 DCI 交换机处的到达顺序，因此远端 DCI 交换机可以按序解析拥塞信息。

**限制 VOQ 队列长度以降低尾延迟。** 当持续累积拥塞发生时，VOQ 收集具有相同目的地的流量。然而，VOQ 中的包会阻塞新进入的流量并增加尾延迟。为进一步限制 VOQ 队列长度，远端 DCI 交换机将对应的传输限制插入 ACK。然后，发送方收到 ACK 后，在出发反馈限制和远端 DCI 交换机限制之间选择更严格的一个来调度传输。为降低与广泛部署的 DCQCN 的部署复杂度，ATC 在远端 DCI 交换机部分转发 CNP 作为修改 ACK 的替代方案。

## B. 长距流量控制

**限制 VOQ 使用数量。** 注意在某些生产数据中心中，VOQ 数量可能小于目的服务器数量。在 VOQ 不足的情况下，ATC 使用以下两种机制约束 VOQ 使用：

> **图 10.** ATC 中 DCI 交换机的 P4 交换机流水线。

**利用长距反馈主动调度 DCI 交换机间包传输。** ATC 在本地 DCI 交换机控制长距 inflight 字节数以约束 VOQ 使用数量。本地 DCI 交换机记录转发到长距链路的包总大小。远端 DCI 交换机记录转发到远端数据中心的总包大小，并每 T 周期生成带有此值的长距反馈。本地 DCI 交换机收到长距反馈后，计算 inflight 字节并调度后续传输。注意在远端 DCI 交换机处，当 VOQ 中剩余大小小于一个 MTU 时，对应的包将直接转发以充分利用长距链路。

**VOQ 高利用率时的额外传输限制。** 当活跃 VOQ 使用数量超过阈值 $N_{threshold}$ 时，后续长距反馈将被标记。本地 DCI 交换机收到这些标记反馈后，将数据包转发速率限制为 $K \times C_{longhaul}$，其中 $K$ 为限制因子，$C_{longhaul}$ 为长距链路带宽。为充分利用长距链路，初始 inflight 字节数设为 $M \times BDP_{longhaul} + C_{longhaul} \times T$，其中 $M$ 为带宽保护因子，$BDP_{longhaul}$ 为长距链路 BDP。推荐参数值：$M=2$，$K=3 \times N_{total\_VOQ}$，$N_{threshold} = \frac{2}{3} \times N_{total\_VOQ}$。

**设计权衡。** 我们进行了大量实验，结果表明在大多数情况下 ATC 仅用动态分配 VOQ 方案就能表现良好。然而，我们仍在本节保留主动调度方案（即长距流量控制）以避免极端情况，并使 ATC 因 DCI 交换机有限的缓存使用而可在商用交换机上部署。

**VOQ 预分配。** 在相当大规模的数据中心中，我们提倡使用预分配 VOQ 配置来缓解 VOQ 不足问题。一些数据中心为节省成本将计算和存储资源解耦。由于存储流量具有 incast 特征（如流层数据重建），VOQ 被预分配并固定到存储集群中的目的服务器。

# V. 实现

**DCI 交换机实现。** 如图 10 所示，ATC DCI 交换机流水线可在 Tofino Native Architecture（TNA）上部署。数据包首先经过入向处理，然后是流量管理器（TM），最后是出向处理。ATC 使用长距流量控制限制 DCI 交换机缓存使用，Tofino2 提供高达 12.8 Tbps 吞吐量并支持高达 400GbE 端口速率，满足数据中心间互联的要求。此外，Tofino2 每个端口组有 128 个队列，使 ATC 可在生产数据中心部署。下面介绍关键组件：

**包预处理模块。** 该模块有两个作用：(i) 通过入端口和包头区分数据包和反馈包，然后标记特殊头元数据以识别不同包；(ii) 在到达 DCI 交换机处，清除包头中携带的拥塞标记。

**调度表修改模块。** 收到到达通知包后，对应的调度表将被更新。为减少控制平面与数据平面之间的交互频率，我们在数据平面预处理拥塞信号并记录在较少的寄存器中。例如，对于 TIMELY，我们在数据平面计算时间戳差并记录此 RTT。此外，每个寄存器在交换机 ASIC 上最多有 10K 条目，使 ATC 可在大规模数据中心部署。

**DWRR 配置模块。** 亏缺加权轮询（DWRR）是 TM 调度器使用的基于消息字节的调度算法。与加权轮询（WRR）相比，DWRR 在各数据包长度不等时仍能按权重分配带宽资源。收到反馈包后，控制平面将计算新权重并修改调度配置表。

**拥塞标记处理模块。** 为解决本地 DCI 交换机处的拥塞，它将数据包从本地数据中心推送到出向处理中的拥塞标记处理模块。为与 TIMELY 兼容并解决远端数据中心拥塞，到达 DCI 交换机在出向处理中用时间戳标记数据包，并在入向处理中用时间戳标记对应的到达反馈包。

**反馈包生成模块。** 为确保高速生成，我们使用交换机 ASIC 的镜像功能。数据包在出向被镜像（分配镜像会话并截断包），随后进行修改。我们在寄存器中建立 QP 对关系并修改 RDMA BTH 头中的目的 QP 号。数据包和镜像包通过元数据区分。此外，Tofino2 支持可编程反馈包生成机制，允许任何入向包触发，有助于在本地 DCI 交换机生成 CNP 并简化数据平面。

**ICRC 修改模块。** ICRC 字段是 RoCE 包被网络适配器接受的必需字段。ATC 利用 Tofino ASIC 中的"Hash CRC32"函数根据公式计算 ICRC，并将其添加到通知包末尾。注意 ATC 只需为反馈包（如 CNP）计算 ICRC，这些包只有少量载荷。

**端主机实现。** ATC 直接与 RNIC 硬件级 DCQCN 兼容。对于其他主机驱动控制方法，ATC 需要在收到反馈包时执行拥塞控制算法。幸运的是，新一代 RNIC 展示了灵活可编程的拥塞控制逻辑。例如，NVIDIA 在其 DPU（如 BlueField3）中引入了可编程拥塞控制（PCC）功能。PCC 框架收集拥塞控制事件并支持自定义控制逻辑，便于部署 ATC 及其他需要修改主机侧控制逻辑的方法。我们计划未来用这些方法实现 ATC。

# VI. 性能评估

我们使用真实测试床实验和大规模仿真评估 ATC。主要发现如下：

- ATC 在真实测试床中与 RNIC 硬件级 DCQCN 兼容，具有稳定的高性能，例如将数据中心内部 FCT 降低最多 58%。
- 与主机驱动方法相比，ATC 确保快速拥塞避免，PFC 减少最多 98%，整体平均 FCT 改善最多 75%。
- 与交换机驱动方法相比，ATC 易于部署同时提供大拥塞控制范围，99th FCT 降低最多 38%。

## A. 评估设置

**真实测试床设置。** 如图 11 所示，我们在两个数据中心之间构建了两个测试床，分别使用专用 100Gbps 链路连接，单向距离分别为 100KM 和 600KM。除非另有说明，我们主要在基于真实生产区域数据中心设置的 100KM 测试床上进行评估。DCI 交换机和 ToR 通过 100Gbps 链路连接。每台服务器有一块 NVIDIA 100Gbps RNIC 连接到 ToR 交换机。

> **图 11.** 真实测试床拓扑。我们分别构建了 100KM 和 600KM 互联的两个测试床。

默认 RNIC 硬件拥塞控制算法是 DCQCN。我们基于 § V 在测试床上部署 ATC。我们的 DCI 交换机流水线实现包含约 700 行 P4 代码和 300 行通过 Barefoot Runtime（bfrt）API 的控制平面配置。由于我们没有基于 RNIC 硬件的 TIMELY 和 HPCC，我们使用 DPDK 部署它们。此外，我们正在与一家交换机厂商合作将 ATC 实现到交换机硬件中。

**仿真拓扑。** 在 NS3 仿真中，我们使用与图 1 相同的拓扑。两个数据中心都使用 FatTree 拓扑构建。每个 ToR 交换机连接四台服务器。两个 DCI 交换机之间每条链路的容量为 400Gbps，其他链路带宽为 100Gbps。数据中心内所有链路的传播延迟为 1us，长距链路传播延迟为 400us（80km 距离）。数据中心内交换机和 DCI 交换机的缓存大小分别为 16MB 和 128MB（源自表 I）。为探索 VOQ 使用，我们随后将核心、聚合、ToR 交换机和服务器数量分别改为 16、20、20 和 320，以扩展到更大的数据中心规模。

**参数设置。** 对于 DCQCN，我们使用主要 NIC 厂商建议的参数作为默认值，并按链路带宽比例缩放 ECN 标记阈值。对于 TIMELY，我们使用其论文建议的参数。按照 HPCC 的做法，为 DCQCN 和 TIMELY 添加了基于长距 RTT 的发送窗口以限制 inflight 字节，这些机制称为 DCQCN+w 和 TIMELY+w。对于 HPCC，我们默认将初始窗口设为长距 BDP 以保护吞吐量。我们评估了 Swift 并发现在混合流量场景下其性能与 TIMELY+w 相当，因此省略其结果。对于其他交换机驱动控制方法，我们遵循其论文中的建议。

**工作负载。** 我们创建了一些简单的人工工作负载来评估微基准测试。在大规模仿真中，我们评估分布式存储场景并使用流量追踪 AliStorage，该追踪从生产分布式存储系统收集，比其他流量追踪更接近真实跨数据中心流量。我们调整流生成速率以将平均数据中心内部和跨数据中心流量负载设置在 20% 到 50% 之间。为进行压力测试，我们以 20% 负载生成跨数据中心 incast 流量。

**性能指标。** 我们有四个主要指标：(i) 平均/99th 尾 FCT；(ii) 单流实时带宽；(iii) 实时网络队列；(iv) PFC 暂停持续时间。

## D. 设计选择

**VOQ 使用。** 我们在之前的实验中监控 VOQ 使用数量，发现在数据中心内部流量主导场景下最多使用 20 个 VOQ。然后，我们扩展到 320 台服务器和对应 FatTree 拓扑的更大数据中心规模。我们将数据中心内部链路带宽重新分配为 400Gbps，并使用四条 800Gbps 链路连接 DCI 交换机。数据中心内部交换机和 DCI 交换机的缓存大小分别为 32MB 和 512MB。我们重现数据中心内部流量主导场景并再次监控 VOQ 使用。此时最大使用数量变为 58。注意 VOQ 使用不与数据中心规模成比例增长，原因有二：(i) 更大的数据中心有更多冗余结构带宽，因此在远端数据中心更难触发一致的混合拥塞，VOQ 可以快速释放；(ii) 在更大的数据中心中，本地 DCI 交换机连接更多核心交换机，因此长距流倾向于在传输到长距链路之前在本地 DCI 交换机处创建拥塞，可以通过出发反馈提前缓解。

从这些实验中，我们注意到在大多数情况下，VOQ 最大使用数量远小于端主机。对于商用交换机 ASIC Tofino2（128 个队列），我们将 $N_{threshold}$ 设为 86，在我们的实验中不会被触发。然而，我们仍保留长距控制以避免极端情况。为对长距流量控制机制进行压力测试，我们将单向跨数据中心流量工作负载设为 30%，发送方侧数据中心内部流量设为 20%，接收方侧数据中心内部流量设为 50%。我们进一步添加 10% 的跨数据中心 Incast 流量。我们监控 VOQ 使用，发现 VOQ 最大使用数量达到 106。我们比较有无长距流量控制的 ATC。对于有长距流量控制的 ATC，我们选择用商用交换机 ASIC Tofino2 评估性能，因此将 VOQ 总数设为 128，$N_{threshold}$ 设为 86。图 28 显示了结果。可以看到，无长距流量控制的 ATC 可以将数据中心内部流量平均 FCT 显著改善 91%，同时将跨数据中心流量平均 FCT 改善 52%。第二个观察是，有长距流量控制的 ATC 也可以使数据中心内部流量受益 88%，表现与无长距流量控制的 ATC 类似。此外，虽然有长距流量控制的 ATC 在跨数据中心流量的 99th FCT 上有所妥协，但仍可将平均 FCT 改善 33%。

> **图 27.** 不同 ATC 配置（数据中心内部流量 20% 负载 + 随机接收端跨数据中心流量 10% 负载 + 8 个固定接收端跨数据中心流量 40% 负载）。

> **图 28.** 不同 ATC 配置（数据中心内部流量 20% 和 50% 负载 + 跨数据中心流量 30% 负载 + Incast 流量 10% 负载）。Dynamic ATC 表示有长距流量控制的 ATC。Ideal ATC 表示无长距流量控制的 ATC。

**VOQ 预分配。** 我们随机选择八台端主机作为接收者并设置跨数据中心流量 40%。然后，我们添加 10% 的随机跨数据中心流量和 20% 的数据中心内部流量。我们比较两种 ATC 配置：8 个预分配 VOQ 的 ATC 和动态 VOQ 的 ATC。图 27 显示了结果。可以看到，预分配 ATC 将数据中心内部流量平均 FCT 降低 50%，跨数据中心流量降低 51%。这表明 HoL 问题在长距传输中很严重，少量 VOQ 就可以带来很大改善。

# VII. 讨论与未来工作

**区分跨数据中心和数据中心内部流量并非易事。** 在当今的云网络中，虚拟子网技术已被广泛部署在跨 DC 环境中以方便管理。该技术将 IP 与 DC 位置解耦。由于 RDMA 完全在 RNIC 硬件中实现传输功能（如拥塞控制逻辑），对于有限的片上 SRAM 来说，维护始终最新的 IP 到 DC 映射是不可行的。这种笨拙的方法也放弃了使用虚拟子网的管理好处。此外，即使我们付出代价采用这种方法，数据中心内部和跨数据中心流量之间的吞吐量不公平性仍会降低性能。

**长距丢包恢复需求。** 关于丢包恢复的研究很多，但它们无法与长距通信的特征（如大 base-RTT 和随机丢包）兼容。一些交换机驱动机制保护重要包并消除超时。例如，TLT 在端主机标记重要包并使用颜色感知丢弃方法选择性丢弃不重要的包。Lightning 增强交换机直接向发送方发送丢包通知。然而，当丢包发生在长距链路或远端数据中心时，发送方仍遭受长反馈环路。此外，Mellanox ConnectX RNIC 实现了有损 RoCE 加速，包括有限发送窗口和拥塞控制优化（如慢启动）。然而，随机丢包引起的 NACK 可能导致虚假的流速率降低。本文中，ATC 主要关注速率控制，将长距链路丢包恢复留作未来工作。

**RNIC 硬件限制对长距性能的影响。** 商用 RNIC 通常采用无 DRAM 架构以降低成本、功耗和面积。因此，RNIC 只能在芯片上缓存少量队列对（QP）和工作队列元素（WQE）。长距传输由于长 base RTT 频繁消耗大量片上内存，导致频繁缓存（如 WQE 缓存）未命中和显著性能下降。最近的工作 SRNIC 通过提出无缓存 QP 调度器和无内存选择性重传方法来最小化大多数片上数据结构。这些工作与 ATC 正交且互补。我们相信 RNIC 架构的发展将增强跨数据中心 RDMA 网络的性能，包括高可扩展性和大规模快速丢包恢复。

**可编程交换机改进。** ATC 要求控制平面和数据平面之间的高效交互和高工作负载处理。然而，最先进的可编程交换机在此交互中面临限制，主要由于低性能交换机 CPU、交换 ASIC 与交换机 CPU 之间慢速 PCIe 以及交换 ASIC 中有限内存等约束。最近的工作尝试使用 CPU 或 FPGA 等外部设备提高包处理性能并实现 Tbps 吞吐量。这些工作与 ATC 正交，我们相信可编程交换机的发展将改善 ATC 的性能，包括快速反应和高可扩展性。此外，我们正在与一家交换机厂商合作将 ATC 实现到交换机硬件中。

# VIII. 相关工作

近年来，大量流量控制方法被提出。我们已在 § III 中讨论了密切相关的方案（如 Azure、BFC、Annulus）。这里仅概述其他一些尚未讨论的想法。

**接收方驱动速率控制。** 最近一系列工作（pHost、NDP、ExpressPass 和 Homa）旨在使用接收方驱动的信用主动分配链路带宽。具体而言，pHost 和 Homa 假设网络核心无拥塞。然而，由于超订的数据中心互联拓扑，拥塞很容易在 DCI 交换机处发生。ExpressPass 和 NDP 需要全交换机修改或高级网络支持。此外，Aeolus 通过选择性丢包缓解"第一 RTT 问题"。然而，它在长距 RDMA 网络中会遭受缓慢的丢包检测并导致严重性能下降。为避免上述问题并便于商用 RNIC 部署，ATC 选择与发送方驱动速率控制方法协作。

**包调度方案。** 为实现近最优延迟，pFabric 需要交换机上的细粒度优先级调度逻辑和端主机上的正确流大小信息，难以部署。PIAS 使用交换机中的多级优先级队列消除了对流大小的预先了解。QJUMP 基于每个应用手动指定优先级。这些调度方案主要与速率控制正交。最近的工作 Bolt 监控所有交换机的队列长度和端口链路利用率以评估网络负载信息并生成反馈给发送方以改善网络利用率。SFC 也监控所有交换机的队列长度并计算暂停持续时间回发送方以缓解队列堆积。然而，这两种方案都需要在所有交换机上部署，而 ATC 仅涉及 DCI 交换机的修改。

**WAN 传输。** 传统的基于丢包的 WAN 传输协议（如 Cubic）存在高丢包和深排队延迟。为避免这些问题，后续协议（如 Vegas、Copa、BBR）利用延迟信号检测拥塞。然而，这些方法仅考虑 WAN 场景，会抑制数据中心内部流量的性能。ATC 与这些基于延迟的 TCP 机制兼容，使用与基于延迟的 RDMA 机制相同的部署方法，直接从 DCI 交换机生成延迟信号。我们未来将结合它们。

# IX. 结论

本文重新架构了跨数据中心 RDMA 网络的流量控制，提出了 ATC——一种易于部署的解决方案，聚焦于缓解混合流量拥塞，作为现有主机驱动方法的构建块。通过在两侧 DCI 交换机上部署，ATC 可以将控制环路缩短到单数据中心尺度并聚合整个数据中心的拥塞信息。我们在商用 P4 可编程交换机上实现 ATC，并通过真实测试床实验和大规模仿真进行评估。大量评估证实，ATC 是增强跨数据中心 RDMA 网络性能的有前景的基座。我们相信 ATC 是迈向未来高速跨数据中心 RDMA 网络流量控制的起点。本工作不涉及任何伦理问题。
