# Proposed-R1 首版实现与验证

依据：`docs/Proposed拥塞控制方案_20260924.md`，2026-09-24。
这是该设计第 21 节首版主线的实现，不表示 E1–E3 性能验收全部通过。

## 文件与控制路径

- `longhaul-convergence.cc`：`proposed` 进入 R1；`proposed-legacy` 进入原 `ResearchSetup()`；配置及元数据。
- `longhaul-proposed-r1.h`：组/QP 登记、接收状态、序列化报文、源侧历史预测、动态预算、近源 CNP 与日志。
- `qbb-net-device.{h,cc}`：可选的单 PG token bucket、链路本地控制接收入口、每 PG 累计暂停时间。
- `broadcom-egress-queue.{h,cc}`：只新增 FIFO 队首观察，用于出队前判断信用。
- `run-research.py`：新旧算法与同执行器消融；`verify-proposed-r1.py`：从日志独立重放信用并检查守恒。
- `longhaul-proposed-test.cc`：历史公式、真实暂停、控制消息丢失、版本校验与有限流集成测试。

数据仍由原交换机 MMU 准入并进入原 FIFO。首版强制该 WAN PG 只属于一个登记组，
因而该 FIFO 就是组队列；没有增加旁路无界缓存。未启用整形的设备仍走原调度逻辑。

逐包出队先检查 PFC、物理端口和信用，信用不足时定时唤醒。最大信用为实际最大
数据帧 M；本次 1000 B payload 的 DCQCN 帧为 1048 B。更新速率先结算旧速率，
不会重新赠送信用；零速率停止该 PG，但保留优先级 0 的控制消息和后续恢复入口。
已经开始序列化的包不能撤回。

接收侧按 200 µs 周期发送完整 `GROUP_STATE`，队列危险/PFC 事件发送 `ALARM`；
源侧按报告周期发送 `APPLY_STATUS`。报文使用本实验私有 IP 协议号 249，含版本、
组、epoch、seq、采样区间、队列/峰值、累计字节、服务、预算、有效期和执行信息。
三类消息经过真实 DCI 链路的优先级 0 排队、序列化、传播、接收处理和错误模型。
接收只允许当前固定组/epoch，拒绝旧序号；不会用旧报告回写新预算。
这是 ns-3 链路本地协议原型，不是商用 RoCE 报文格式或 ICRC 兼容性证明。

接收出口空闲时仍保持配置容量，不能把低吞吐解释成低容量。已知 PFC 立即上报
零服务；普通报告按该 PG 在周期中的暂停时长折算服务。实际服务再次出现后恢复。
不具备对未来暂停的保证。

源侧每 50 µs 仅使用已收到的快照和本地实际出队历史。历史保存逐包记录，
以每个包的序列化时间、传播时间和接收处理延迟计算预计入队时刻；按时间递推并
在每一步截断非负，保留区间峰值。相比设计稿的 50 µs 分箱，这一原型使用更精细的
逐包历史，内存规模随历史窗口内包数增长，不声称是固定硬件状态成本。

动态上限遵循设计稿的服务/容量约束、排空时间和按时间归一化的上升斜坡。
无有效快照时用配置容量；过龄/历史不覆盖时进入 STALE，禁止增加上限；
危险队列、暂停或已承诺峰值越界时停止新注入，仍靠后续报告恢复。
预测误差在未来报告网格发布后与同一采样时刻配对，首轮不反馈误差裕量。

近源 CNP 由真实源队列持续压力及逐流超额输入触发；短暂静默不会立即移除流，
仍有本地排队/暂停证据的流继续保留份额。没有读取预知完成时间或剩余流大小。
每流通知间隔不小于 50 µs，记录透传 CNP/带拥塞标记 ACK，在同一间隔避免补发。
这是兼容透传模式，原 ECN/CNP/PFC 仍工作；未实现受控出口 ECN 托管。
网关放宽目标并不等同于 RNIC 主动提速，日志中的 `sender_limited` 只表示采样周期
内源队列空且输入低于目标，不是需求不足的证明。

## 参数

原六项 CLI 不变，以下参数写入 `--conf`：

| 配置键 | 默认值/规则 |
|---|---|
| RESEARCH_RECEIVER | 显式指定接收主机；runner 设为 4 |
| RESEARCH_OUTPUT | R1 控制 CSV 路径；未设置时从 metadata 路径派生 |
| RESEARCH_TARGET_UTIL | 0.98 |
| RESEARCH_DEADBAND | 0.05，逐流超额门限 |
| R1_PREDICTOR | 0 实际历史；1 最新快照反应；2 静态容量整形 |
| R1_REPORT_PERIOD | 0.0002 s |
| R1_CONTROL_PERIOD | 0.00005 s |
| R1_QREF | 0 表示按接收容量 × 40 µs 推导 |
| R1_SOURCE_HIGH | 250000 B，低水位为其 1/4 |
| R1_EMERGENCY | 0 表示接收危险水位取配置共享池的 1/4 |
| R1_SOURCE_EMERGENCY | 0 表示源危险水位取配置共享池的 1/4 |
| R1_TAU_Q | 0 表示 max(2(df+db), 4Tr) |
| R1_TAU_UP | 0 表示 max(df+db, 4δ) |
| R1_CNP_INTERVAL | 0.00005 s；不允许小于此值 |

危险水位的默认值是有限共享池中的开发预留，不是根据 MMU 动态 PFC 门限证明的
安全余量。其他交换队列也会占用共享池，必须用实际缓存/PFC/丢包结果判断。
R1 不读取旧 `RESEARCH_QREF`、预测权重和按周期增加比例；实际参数看 `r1_parameters`。

## 已验证结果与边界

普通有限流检查：四个源各 100 MB，10 ms 同时开始，主机/接收链路 100 Gbps，
WAN 200 Gbps、单向传播 1 ms、无发送窗口限制，仿真 120 ms。
输出位于 `/tmp/proposed-r1-final-0924`，属于可清理的验证产物。

| 版本 | 完成流数 | 最大 FCT（ms） |
|---|---:|---:|
| DCQCN | 4/4 | 62.288085 |
| 旧 Proposed | 4/4 | 45.868664 |
| R1 实际历史 | 4/4 | 53.950059 |
| R1 最新快照反应 | 4/4 | 53.950059 |
| R1 静态整形 | 4/4 | 53.950059 |

R1 三种模式均通过逐包信用检查。源入口、WAN 出口、接收入口及接收出队均为
419200000 B（包括 48 B/帧报头）；交换机准入丢包为 0。接收事件峰值 1048 B，
源队列采样峰值 9768408 B，全网队列采样峰值 9768602 B。源/全网峰值是周期
采样，不能作为精确事件峰值。普通场景 R1 发出 66 枚合成 CNP。

该场景没有展示预测独立收益：三个 R1 模式结果相同，且均慢于旧 Proposed。
实际整形把主要积压移到了源侧，不能仅凭接收队列降低声称方案更好。

公式测试覆盖设计稿例 17.1（6.5 MB）与“先空闲、后突发、最后排空”的区间峰值。
集成测试复用有限流输入，额外注入接收出口 2 ms PFC、5 ms 控制报告丢失以及旧
序号/epoch，检查停止、STALE、恢复、最终字节守恒和全部流完成。该测试已通过，结果位于
`/tmp/proposed-r1-fault-0924`：4/4 完成，最大 FCT 62.786160 ms；观察到 EMERGENCY、
RECOVER、STALE、TRACK；两份错误版本/序号消息被拒绝，准入丢包为 0，逐包信用检查通过。
接收事件峰值为 2424024 B，最大预测低估为 2222498.5 B。这符合“源侧不能预知
远端突发暂停”的边界，不能用普通无竞争场景的零低估掩盖这一误差。

可先执行 `build/examples/LonghaulCC/ns3.39-longhaul-proposed-test-optimized` 运行公式测试；
传入与主程序相同的 `--conf`、`--flow-file`、`--cc=proposed`、`--stop-time=0.12`
即可运行上述故障测试。使用 runner 生成的 1 ms WAN、4×100 MB 输入，并将配置中的
所有输出路径改到独立目录，避免覆盖正常实验。

以下仍未作为本版实现/结论：多源 DCI、一般多跳/ECMP、域内竞争预算、ECN 托管、
端侧主动提速、严格公平调度、误差校准反馈及统计意义上的性能优势。错误拓扑/额外
竞争组会明确报错。没有改写旧 Proposed 控制函数，也没有改变 DCQCN RNIC 算法。
