# LonghaulCC 程序审查报告

审查日期：2026-09-22。对象：当前工作区的 `longhaul-convergence.cc`，并追踪其调用的 RDMA、Qbb、交换机及 INT 实现。**本次没有修改源码、配置文件或已有实验结果；只新增本报告。** 已有未提交改动按当前状态审查。Proposed 的算法设计不在范围内，仅检查其开关是否可能影响基准。

## 1. 结论

**目前不能认定 DCQCN、HPCC、TIMELY、FRP 四个基准正确可信。应先修复实验与模型的适配问题，再做代码精简。**

| 基准 | 已确认部分 | 当前结论 |
|---|---|---|
| DCQCN | mode=1，ECN→ACK 的 CNP 标志→发送端降速路径存在；有限单流及小型 incast 完成 | 可继续验证的基础，但默认 1 TB 流、统计口径及未充分验证的拥塞恢复过程阻止正式验收 |
| HPCC | mode=3，启用 INT，关闭 PowerTCP 分支 | **当前跨 DC 路径超过 INT 容量，有越界和跳过控制更新问题，不能作为基准** |
| TIMELY | mode=7，使用发送时间戳回显计算 RTT | **当前阈值低于无拥塞跨 DC RTT，会无拥塞降速，不能据此评价算法表现** |
| FRP | 底层存在 mode=13 的反馈实现 | **入口不支持、反馈未启动，地址编码也不兼容，尚未接入这个实验** |

这里的“完成传输”只证明相应输入下应用和传输路径跑通，不等于算法论文复现、拥塞控制正确或公平性达标。

## 2. 必须优先处理的正确性问题

### P1-1：HPCC 的六跳路径超出五跳 INT 容量

位置：`src/network/utils/int-header.h:84`、`int-header.cc:37`；`src/point-to-point/model/rdma-hw.cc:905`；入口 `longhaul-convergence.cc:738` 附近的 INT 模式设置。

默认跨 DC 流 `0→41` 的路径结构为：主机→叶交换机→脊交换机→网关→对端网关→对端脊交换机→对端叶交换机→主机。共 **6 台交换机、7 条链路**。

`IntHeader::maxHop=5`，`PushHop()` 用 `nhop % maxHop` 覆盖槽位，却继续递增 `nhop`。第六跳覆盖第一跳，接收端得到 `nhop=6`。首次 `UpdateRateHp()` 只用 `NS_ASSERT` 检查容量，随后按 `ih.nhop` 循环复制到五元素数组：断言开启时会失败，关闭时访问越界。后续更新又被 `ih.nhop <= maxHop` 条件挡住。

实测 optimized 构建的 HPCC 跨 DC 100 MB 流仍正常退出并完成。这恰好说明退出码和 FCT 无法识别此问题；不能把这次运行当作有效 HPCC 结果。越界具体破坏了什么状态未用调试器确认，不做推断。

最小修复方向：为当前真实路径提供足够的 INT 槽位，并同步确认序列化大小、交换机写入及发送端数组边界。不要截掉一跳来绕过错误，那会丢掉潜在瓶颈反馈。

### P1-2：默认 1 TB 流不兼容底层字节与序号处理

位置：`flow-longhaul-s0.txt:2`，S1–S5 也有同样输入；`rdma-hw.cc:646–648`、`:465–468`、`:550` 附近；`rdma-queue-pair.h:160`、`rdma-queue-pair.cc:120`。

`GetBytesLeft()` 返回 64 位剩余字节，但 `GetNxtPacket()` 先转成 `uint32_t`，再限制到 MTU。对于 1,000,000,000,000 B：

- 初始低 32 位为 3,567,587,328 B。
- 当已发送这么多字节、剩余量成为 `2^32` 的整数倍时，转换后的 payload 为 0；`snd_nxt` 不再前进，仍可能持续生成空载荷包。
- 此外，线上数据/ACK 序号及接收端 expected sequence 为 32 位，发送端 ACK 更新仅比较大小，没有完整的序号回绕处理。

因此问题不只是“1 TB 在停止前传不完”。它会在某个字节位置破坏发送进度；短时间 smoke 可能尚未触发。此处是源码和整数运算确认，未运行完整 1 TB 场景。

最小修复方向：当前先用明显小于 `2^32` B 的有限流，例如 100 MB、500 MB 或 1 GB，并安排足够的控制反馈周期。只改 payload 转换顺序不能解决线上序号回绕。需要长时间持续负载时，应明确选择有限流批次还是完整扩展传输序号，不能把 1 TB 当作无限流占位。

### P1-3：TIMELY 的绝对 RTT 阈值使无拥塞跨 DC 流降速

位置：`config-longhaul-common.txt:22–24`；`rdma-hw.cc:1221–1279`；入口 `longhaul-convergence.cc:970–982`；`qbb-net-device.cc:492–500`。

当前 `TLow=5 ms`、`THigh=10 ms`、`MinRtt=10 ms`。单是跨 DC 传播 RTT 已约 10.018 ms。并且 `NIC_DELAY=15 μs` 是所有 Qbb 设备的默认值，交换机接收也会执行；这条七链路路径往返共有 14 次接收处理，再增加约 210 μs，尚未计入完整包序列化和排队。

TIMELY 判断 `rtt > THigh` 后直接走乘性减速，不看梯度是否为零。故稳定、空队列的跨 DC 路径也会减速。

实测 500 MB 单流：FCT 52.918842 ms，DCI 采样队列峰值 0、DCI ECN 计数 0、全网 PFC 事件 0；发送有效载荷速率后段约 89.84–89.92 Gbps，低于初始约 95 Gbps。结合上述分支可解释该下降；本次未直接导出逐次 `m_rate` 和 RTT 控制日志。

最小修复方向：先确定 NIC 延迟应仅施加于主机还是每个设备；按最终模型测量无拥塞 RTT，再确定高低阈值及梯度归一化基准。跨 DC 和 DC 内流不能直接共用一组未经校准的绝对 RTT 阈值。不要为了得到好看的曲线盲目调参。

### P1-4：FRP 不是增加一个算法名称就能启用

位置：入口 `longhaul-convergence.cc:669–675`、`:217–232`、`:995–1006`；`switch-node.cc:561–570`、`:542`；`rdma-hw.cc:1464–1477`。

三个独立问题：

1. `ResolveCcMode()` 没有 `frp→13`。实测 `CC frp` 直接报 unknown congestion-control algorithm 并终止。
2. 入口没有设置 `SwitchFeedbackEnabled=true`，也没有调用 `StartPeriodicFeedbackMechanism()`。只补 mode=13 仍没有周期反馈。旧 `PowerTCP/crossDC-evaluation.cc:1447–1453` 有相应接入，不能假定本程序继承了它。
3. 本程序所有地址为 `11.0.0.(node+1)`，FRP 根据 `(ip >> 16) & 0xff` 判断 DC。所有主机都会得到 DC=0，跨 DC 流会被当作内部流，进入不同调速分支；交换机源 DC 统计同样失真。

最小修复方向：同时落实模式映射、交换机反馈启动、DC 身份表达，保持三者一致后再验证 FRP。报告不将现有 FRP 标为已验收，也不凭旧入口曾能运行而确认此入口正确。

### P2-1：发送速率不是单调发送字节计数，且采样丢失首段

位置：入口 `longhaul-convergence.cc:270–285`、`:421–467`；`rdma-hw.cc:592–594`。

`sender-rate.csv` 使用 `snd_nxt` 差分。`snd_nxt` 是下一发送序号，NACK 恢复时会回退到 `snd_una`，所以不是实际发送字节总数。回退后检查 `snd_nxt >= last_tx_seq` 会跳过部分采样，重传开销也无法准确反映。这影响以发送速率判断降速时刻、收敛和链路负载。

首次发现 TX/RX QP 时直接把当前计数存为基线，已经发生的首段传输被舍弃。实测 DC 内 HPCC 1 MB 流在 154.053 μs 完成，发送 CSV 唯一样本却为 0。跨 DC 100 MB DCQCN 流首段也漏记约 1.205 MB 发送字节。

最小修复方向：区分控制器目标速率、实际发送字节速率、接收有效字节速率。实际发送用单调的逐 QP 计数或现有发送 trace；接收继续用去重后的 `m_recv_bytes`。在流启动时建立零基线，正确记录不足一个采样周期的完成段。只画吞吐率并不要求增加复杂监控框架。

### P2-2：DCI 的 rx_bps 命名与实际计数含义不一致

位置：入口 `longhaul-convergence.cc:470–495`；`switch-node.cc:241`。

`totalBytesRcvd` 在交换机把包交给**出口设备**时增加，源码也注明不是入口端口接收计数。因此 CSV 的 `rx_bps` 实际接近该出口的入队/供给速率，不是对端收到的 DCI 链路吞吐率。也不能简单换成对端同名计数就解决。

最小修复方向：若需要入队速率，准确命名并说明准入/丢包边界；若需要 DCI 到达速率，在对端真实接收位置计数。主机应用 goodput 应继续独立统计。

同一 CSV 中 PFC 计数来自全网所有设备，每条方向记录都写相同累计值；发送和接收同一个 PFC 帧各触发事件。它是全网事件数，不是该方向的独立 PFC 帧数。ECN 计数则是经过 DCI 出口的已标记数据包数，不能视为 DCI 本地新产生的标记次数。现有 `pfc.csv` 保留设备和事件类型，足够用于重新定义统计，无需重新搭建采集系统。

### P2-3：RTT、窗口和 standalone_fct 的计算口径不一致

位置：入口 `longhaul-convergence.cc:200–208`、`:288–293`、`:350–352`、`:970–982`；`rdma-hw.cc:292–294`；`custom-header.cc:339`。

- `pairRtt` 只计双向传播加一份 payload 序列化，没有包含上述每跳 NIC 延迟、完整数据头和 ACK 序列化。应标为模型近似 RTT，不能冒充实测空载 RTT。
- 入口传入按路径瓶颈算的 BDP，但 `AddQueuePair()` 在 win 非零时重新按 NIC 带宽×baseRtt 计算窗口。当前全路径瓶颈恰好等于主机 NIC 速率时影响有限，异构瓶颈下传入的窗口会被覆盖。`HAS_WIN` 在这里主要表现为开关。
- `GLOBAL_T=1` 将跨 DC 最大 RTT 用于 DC 内 QP；这会改变 HPCC 平滑时间和窗口。当前 small 流文件是 DC 内流，不能按跨 DC 时间尺度解释。
- `standalone_fct` 扣除 INT 字节，又使用含 14 B L2 的静态头大小；实际发送路径添加 2 B PPP，且 HPCC/TIMELY 携带不同遥测头。因此它不是严格的同算法独立流 FCT。

实测 DC 内 HPCC 1 MB 的参考值为 90 μs，而实际 FCT 为 154.053 μs，即使没有竞争也会出现明显大于 1 的归一化 FCT。该比值同时混入模型口径误差和算法开销。

最小修复方向：明确区分理论下界与同算法独立流基准。若用于 slowdown 比较，优先使用同拓扑、同算法、同大小的独立流实测 FCT；若保留公式，则把全部假设写清楚并统一字节与时延口径。

## 3. 控制器实现审查边界

DCQCN 的接收端回显 ECN、发送端 alpha 更新、定期降速、快速恢复/主动增加/超增分支均存在；HPCC 使用发送字节 INT 而非 PowerTCP 的到达字节分支；TIMELY 使用发送时间戳而不是伪造 RTT。这些连接方向是正确的。并不意味着所有长距适配已完成。

DCQCN 这里通过逐 ACK 的 CNP 标志反馈 ECN，属于 HPCC 仿真代码常见实现方式，不应直接写成真实 RNIC 独立 CNP 抑制/定时行为的完整复现。TIMELY 的空 `FastReactTimely()` 和按 ACK 序号划分更新周期不能仅凭“函数为空”判为错误，但 HAI 的触发及步长应按所选参考实现明确说明；当前 50/100 Mb/s 的 AI/HAI 也不能自动宣称逐项等同论文。相关参考为 [HPCC 作者仓库的 RDMA 实现](https://raw.githubusercontent.com/alibaba-edu/High-Precision-Congestion-Control/master/simulation/src/point-to-point/model/rdma-hw.cc) 和 [TIMELY 原论文 Algorithm 1](https://conferences.sigcomm.org/sigcomm/2015/pdf/papers/p537.pdf)。本次不是完整逐行上游差异审计。

HPCC 还存在需在修复跳数后验证的表示范围：INT 队列 17 位、单位 80 B，超过约 10.486 MB 会截断回绕；时间戳 24 位纳秒，周期约 16.777 ms；字节计数周期为 128 MiB（INT_MULTI=1），200 Gbps 下约 5.37 ms。这里要求的是**相邻有效遥测样本间隔**不超过可消歧范围，不是说 RTT 大于 5.37 ms 就一定错误。拥塞/PFC 使样本稀疏时要实际验证。当前 DCQCN incast 的 DCI 队列采样已达 14.563 MB，说明该实验平台有进入队列字段风险范围的可能，但不证明 HPCC 运行一定出现同样队列。

FRP 的底层超时恢复由后续非瓶颈反馈触发，并非独立调度的超时事件；端口周期只处理当期有流量的记录。若反馈完全消失，不会单凭经过 100 μs 自动恢复。这个语义是否符合目标 FRP 方案需要与算法定义核对；本报告不擅自改写方案。

基准隔离方面，普通配置未设置 research 输出，`ResearchSetup()` 直接返回，当前默认基准不会启用该扩展。但当配置同时包含 `RESEARCH_OUTPUT`、非零 `RESEARCH_CONTROL` 时，`CC dcqcn` 仍可能运行额外控制而标记为 dcqcn。建议在选择基准时固定关闭主动 research 控制，作为一项集中的实验身份约束。

## 4. 简洁性和效率：建议做的小改动

这些建议放在正确性修复之后，不建议为 64 主机、少量配置输入重构框架。

| 位置 | 最小调整 | 收益和边界 |
|---|---|---|
| `CountDciEcn():317` | 直接对只读 packet 调用 `PeekHeader`，去掉 `Copy()` | 每个 DCI 包少一次 Packet 对象复制；不改变计数定义 |
| `SampleDciLink():496` | 去掉每 100 μs 的主动 flush，正常结束统一关闭 | 减少密集 I/O；异常退出时可能少量缓冲数据未落盘，按实际需求取舍 |
| 交换机 MMU 配置 `:860–881` | 将设备转换、链路速率/延迟读取、ECN 配置移到八队列循环外 | ECN 按端口只配一次，队列循环仅保留 headroom 设置与累计 |
| `WriteRate():169` 等 | 输出已成功打开后不再逐行检查；已校验的固定节点关系不必每次采样重复检查 | 缩短稳定热路径；QP 尚未开始、已经完成等真实生命周期判空仍保留 |
| `SetRoutingEntries():398` | 用 const 引用遍历 next-hop vector | 避免不必要的小容器复制，无需更换整个图结构 |
| `FlowInput:136` | 将 `maxPacketCount` 改成 `size_bytes`，明确 sport/dport 和字段单位 | 当前名字表示包数，实际传入字节数，容易导致实验配置错误 |
| `main()` | 如需整理，仅按建链、配置 MMU、安装 RDMA 三个阶段提取普通函数 | 让实验流程可读，不引入基类、工厂、注册器或统一配置框架 |
| `ReadKMap` / `ReadPmaxMap` | 现有短函数可直接保留 | 不值得为了少量重复引入通用反射式解析 |

`FindFlow()` 只在完成时线性查找，当前流数很少，不值得额外维护索引。BFS 和多层 map 主要在初始化阶段运行，也不是当前优先性能瓶颈。真正密集的是逐包事件、复制与 CSV 写出。

保留必要检查：配置/拓扑/流文件读取成功、输出能打开、主机 ID 合法、必需 DCI 存在。补充检查只集中在会使结果无效或死循环的约束：采样周期和 MTU 非零、有限流大小兼容、HPCC 跳数容量、算法模式与主动扩展互斥，以及 ECN 速率表覆盖当前链路。无需给每个参数增加复杂验证。现有 NS_ASSERT 在 optimized 下不能充当这些必要契约的唯一保障。

## 6. 后续最小验收顺序（本次不实施）

1. 修复 HPCC 容量、有限流输入、TIMELY RTT 基准、FRP 接入与 DC 编码。先让每个基准运行的是预期算法。
